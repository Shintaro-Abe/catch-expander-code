# 実行診断役（第 1 段階）の使い方

> 「実行診断役」「カスタムツール」「診断結果」「受け渡し用の診断結果」「足取り」は、正式な名称として確定し、`docs/glossary.md` に登録済み（2026-10-05）。
> 設計は `.steering/20261004-execution-diagnostician/design.md`、受け入れ条件は同 `requirements.md`。
> **実際の LLM と AWS の記録を使った動作は未検証**（任意条件 O1。実施にはユーザーの承認が要る）。
> 自動テストが確かめているのは、ツール・上限・検証・照合・起動の経路であり、診断の当たり外れではない。

## 1. 何をするものか

実行 ID を 1 つ受け取り、その実行の記録（実行レコード・段階・イベント・プロンプト記録）を
モデルが自分で選んで調べ、固定の構造の診断結果を返す。

- 記録を読むツールは読み取り専用で、コードが渡した実行 ID の記録しか読めない。
- 診断結果の根拠は、ツールが実際に返した根拠 ID とコードが照合する。
- 入力の検証は、ツールの中身（`ToolSession`）だけで行う。SDK に渡す入力スキーマは、項目の名前と説明だけの緩いものにしてある。
  SDK の MCP サーバーは、ハンドラーの前にスキーマで入力を検証するので、厳しいスキーマを渡すと、不正な呼び出しが
  ハンドラーに届かず、足取りに残らず、呼び出し総数にも数えられないためである。
- モデルが使えるのは、自分で定義した 5 個のツールだけ。それ以外のツールが見えたら、診断を中断する（§4.1）。
- 受け渡しに入る「例外の型」と「コードの場所」は、記録の文字列をそのまま使わない。例外の型は、コード側の許可一覧
  （組み込みの例外クラス、コードに定義されたクラス、依存ライブラリの固定の一覧）にある名前だけ。コードの場所は、
  スタックトレースの最初のブロックから取り、実際のコードにその関数・その行があるものだけ。
- 行うのは「調べる」と「対処を提案する」まで。コードの修正、実行のやり直しは行わない。

実装は `src/agent/diagnosis/`。入口は 2 つある。

| 入口 | 起動 | 結果の行き先 |
|---|---|---|
| 手動実行 | `python -m diagnosis <execution_id>` | 標準出力（と、指定すれば受け渡し用のファイル） |
| 失敗時の自動起動 | ECS タスクが失敗し、`EXECUTION_DIAGNOSIS=true` のとき | 失敗通知と同じ Slack スレッドに 2 通目 |

## 2. 手動実行の手順

pytest の既定実行では走らない。次の手順で、人が 1 回ずつ動かす。

### 2.1 前提

| 前提 | 内容 |
|---|---|
| サブスクリプション認証 | Claude Code にログイン済みであること（`claude login`。認証情報は `~/.claude/.credentials.json`）。API キーは使わない。手順は `docs/credential-setup.md` §4 |
| Python の依存 | `src/agent/requirements.txt`（`claude-agent-sdk`、`boto3`）が入った環境 |
| AWS の認証情報 | 下の読み取り権限を持つ認証情報（`AWS_PROFILE`、または `AWS_ACCESS_KEY_ID` などの `AWS_*`）と `AWS_DEFAULT_REGION` |

### 2.2 環境変数

| 環境変数 | 必須 | 内容 |
|---|:---:|---|
| `DYNAMODB_TABLE_PREFIX` | o | テーブル名の接頭辞。`<接頭辞>-workflow-executions` と `<接頭辞>-workflow-steps` を読む |
| `EVENTS_TABLE` | | イベントのテーブル名（`<接頭辞>-events`）。未設定なら、イベントを読むツールは `unavailable` を返す |
| `PROMPTS_BUCKET` | | プロンプト記録のバケット名。未設定なら、プロンプト記録を読むツールは `unavailable` を返す |
| `AWS_DEFAULT_REGION` などの `AWS_*` | o | 記録を読むための認証情報とリージョン |
| `DIAGNOSIS_MODEL` | | モデル名。未設定なら `sonnet` |

### 2.3 必要な読み取り権限

| 対象 | 操作 |
|---|---|
| `<接頭辞>-workflow-executions` | `dynamodb:GetItem` |
| `<接頭辞>-workflow-steps` | `dynamodb:Query` |
| イベントのテーブル | `dynamodb:Query` |
| プロンプト記録のバケットの `prompts/*` | `s3:GetObject`（「キーが無い」と「読めない」を区別するには `s3:ListBucket` も要る。無い場合はどちらも `unavailable` になる） |

診断役が使う操作はこの 3 種（`GetItem`・`Query`・`GetObject`）だけで、書き込みは行わない。

### 2.4 実行例

`src/agent/` を作業ディレクトリにして実行する。

```bash
cd src/agent
export DYNAMODB_TABLE_PREFIX=<接頭辞>
export EVENTS_TABLE=<接頭辞>-events
export PROMPTS_BUCKET=catch-expander-prompts-<アカウント ID>
export AWS_DEFAULT_REGION=ap-northeast-1

# 診断結果と足取りを標準出力に出す
python -m diagnosis exec-20261001100000-1b2c3d4e

# JSON で出す
python -m diagnosis exec-20261001100000-1b2c3d4e --json

# 受け渡し用の診断結果をファイルに書き出す（書き出し先は、まだ無いパスにする）
python -m diagnosis exec-20261001100000-1b2c3d4e --handoff-out /tmp/handoff.json
```

終了コードは、診断が `completed` なら 0、それ以外は 1。引数の誤りと、`--handoff-out` の先に既に何かがある場合は 2。
ログは標準エラーに出る。標準出力からは、制御文字（改行とタブを除く）を取り除いてある。

**スタックトレースのフレームは、手元のコードと突き合わせる**。フレームの `/app/x/y.py` は、`diagnosis` パッケージの親
ディレクトリ（手元では `src/agent/`、ECS では `/app/`）の `x/y.py` と突き合わせ、その関数のその行が実在するものだけを
「コードの場所」として残す。失敗した実行と手元のコードの版が違うと、本物のフレームも捨てられる。
失敗した実行と同じ版のコードを取り出してから実行すること。

手動実行では、既定では `diagnosis_completed` イベントは残らない（`src/agent/` からは
`src.observability` を import できないため）。残したい場合は `PYTHONPATH` にリポジトリのルートを足す。
その場合は、イベントのテーブルへの `dynamodb:PutItem` も要る。

## 3. 出力の読み方

| 項目 | 意味 |
|---|---|
| `status` | `completed`（診断結果の提出を受理）/ `incomplete`（上限に達して提出なし）/ `failed`（SDK の失敗、準備の失敗、5 個以外のツールの検出、実行 ID の形式が不正） |
| `stop_detail` | `submitted` / `max_turns` / `max_budget` / `timeout` / `no_submission` / `sdk_error`（SDK の失敗）/ `setup_error`（SDK を呼ぶ前の準備の失敗。環境変数の不足など）/ `tool_isolation_failed`（自分で定義した 5 個以外のツールが見えた）/ `invalid_execution_id` |
| `failed_stage` | 失敗した段階。`analyzing` / `planning` / `researching` / `generating` / `reviewing` / `storing` / `notifying` / `none`（失敗していない）/ `unknown` |
| `cause_category` | 原因の分類。`rate_limit` / `external_service_error` / `research_failed` / `output_validation_failed` / `review_not_passed` / `auth_or_environment` / `insufficient_records` / `unknown` |
| `cause_nature` | 原因の性質。`code_defect` / `transient` / `input_or_prompt` / `environment_or_config` / `unknown` |
| `confidence` | 確からしさ。`high` / `medium` / `low` |
| `action` | 推奨する対処の分類（`retry_later` / `retry_now` / `review_config` / `fix_code` / `no_action` / `human_investigation`）と短い説明 |
| `summary` | 要約（モデルが書いた文。マスク済み） |
| `exception_type`・`code_location` | コードがイベントの記録から取り出した、例外の型とコードの場所。モデルは ID で選ぶだけで、文字列は書かない。例外の型は、コード側の許可一覧にある名前だけ（無ければ `None`）。コードの場所は、スタックトレースの最初のブロックにあり、実際のコードにその関数・その行があるものだけ |
| `evidence` | 有効な根拠（ツールが実際に返した根拠 ID）の件数と、取り除いた無効な根拠の件数 |
| `fixer_eligible` | 「修正役に渡せる」の判定。コードが決める。次をすべて満たすときだけ真: 原因の性質が `code_defect`、確からしさが `high`、対処が `fix_code`、原因の分類が `unknown`・`insufficient_records` でない、有効な根拠 1 件以上、コードの場所 1 件以上、例外の型を取ったイベントが場所の少なくとも 1 件の由来であり、有効な根拠にも含まれる |
| `trace` | 足取り。呼んだツールの順番・検証後の引数・結果の分類・返した根拠 ID の件数・所要時間 |

`incomplete` と `failed` では、診断結果は「不明」（`cause_category=unknown`、`confidence=low`）になり、
それまでの足取りだけが残る。「分からない」（`unknown`・`insufficient_records`）は正当な結果である。

`unknown`・`insufficient_records` 以外の分類で、有効な根拠が 1 件も無い提出は、原因を「不明」に落とす。このとき、
対処は `human_investigation` に、要約と対処の説明は固定の文面に差し替える（モデルが書いた文は出さない）。

根拠 ID の形: `EX-1`（実行の概要）、`ST-<n>`（段階）、`EV-<n>`（イベント）、`PR-<役>-<番号>`（プロンプト記録）。
コードの場所の ID は `FR-<n>`。

ツールの結果の分類: `ok` / `invalid_input` / `not_found` / `unavailable` / `call_limit` / `size_limit` / `internal_error` / `deadline_exceeded`（診断全体の制限時間を過ぎてから始まった呼び出し。記録を読まずに断る。提出も受理しない）。

ツールの結果（モデルに返る内容。足取りの検証で見ることがある）に出る、固定の文字列:

| 文字列 | 意味 |
|---|---|
| `<unlisted>` | イベントの `payload.error_type` が、例外の型の許可一覧に無かった。記録の文字列をそのまま返さず、これに置き換える。この型は、受け渡しにも入らない |
| `<omitted>` | イベントの外側の項目（`timestamp`・`status_at_emit`・`event_type`）が、文字列でも数でもなかった（配列、辞書など）。中身を返さず、これに置き換える |
| `<binary>` | 記録の値がバイト列だった |
| `[MASKED]` | トークン・キーの形をした部分。対象: Slack のトークン（`xox…`・`xapp-`）と Webhook の URL、GitHub・GitLab のトークン、`sk-` で始まるキー、Notion のトークン、AWS のアクセスキーと `aws_secret_access_key` の値、`Bearer` の値、`Authorization: Basic` の値、URL の中の認証情報（password の部分。ホスト名は残る）、JWT、`AIza` で始まるキー、秘密鍵の PEM ブロック。`aws_secret_access_key` は、キー名も値も引用符で囲んだ書き方（JSON、Python の辞書の表示）でもマスクする。記録の辞書では、名前が秘密を表すキー（`secret`・`token`・`password`・`passwd`・`api_key`・`apikey`・`api-key`・`authorization`・`credential` のどれかを含む。大文字と小文字は区別しない）の文字列の値を、丸ごと置き換える。それ以外の、形の決まっていない秘密は、マスクされない |

イベント 1 件が 1 回の上限に収まらないときは、`payload` を空にして `payload_omitted: true` を付ける。それでも
収まらなければ、`evidence_id` と `event_type` だけの最小の形で返す。

## 4. 失敗時の自動起動（フラグ `EXECUTION_DIAGNOSIS`）

- 環境変数 `EXECUTION_DIAGNOSIS` が `true`（大文字・小文字は区別しない）のときだけ有効。**未設定なら無効**で、
  `diagnosis` パッケージは import もされない。
- 有効なとき、ECS タスクが失敗すると、既存の失敗通知を今までどおり送った**後に**診断役を 1 回走らせ、
  診断が `completed` のときだけ、同じ Slack スレッドに 2 通目として投稿する。
- 次の場合は走らせない: Claude のレート制限・使用上限による失敗 / 認証情報の準備より前の失敗 /
  フィードバック処理の失敗 / 実行 ID や投稿先が分からない。
- 診断役の失敗・時間切れ・投稿の失敗は、元の例外・既存の失敗通知に影響しない。認証情報の書き戻しは、
  診断の後に今までどおり行われる（ただし §4.2 の制約がある）。
- 投稿文のうち、要約と対処の補足はモデルが書いた文なので、「未検証」の印を付け、Slack が解釈する書き方を無効化してある:
  メンションと書式の記号（`<`・`>`・`@`・`*`・`_`・`~`・バッククォート・`&`・`!`・`#`）は全角の文字に置き換え、
  リンクになる書き方は崩し（`://` → `[:]//`、`www.` → `www[.]`、`tel:` → `tel[:]`、`mailto:` → `mailto[:]`）、
  不可視の文字・制御の文字（Unicode の Cf・Cc）は取り除く。見出しなどの固定の行には、かけていない。
- 終了時に、イベント `diagnosis_completed` を 1 件残す（終了理由、原因の分類、確からしさ、ツール名の並び、
  件数、所要時間、トークン数、受け渡し用の診断結果）。要約などの自由記述と記録の中身は入れない。

**本番では有効になっていない**。有効にするには `template.yaml` に環境変数を足す必要があり、
あわせて S3 の読み取り権限（`s3:GetObject`、`prompts/*`）を足すのが自然である。どちらも別の作業単位とする。
**有効にする前に、§4.2 の制約をどう扱うかを決めること。**

### 4.1 自分で定義した 5 個以外のツールが見えたら中断する

診断役のモデルには、記録（Web から取った文章などを含む、信頼できない内容）を読ませる。組み込みのツール
（シェル、ファイルの読み書き、通信など）が使える状態だと、記録に仕込まれた指示でそれらを使われうる。
そのため、3 重に備えている。

1. オプションで外す: `tools=[]`、`allowed_tools` は 5 個だけ、`disallowed_tools` に組み込みツールの名前、
   `strict_mcp_config=True`（設定ファイル由来の MCP サーバーを読ませない）、`setting_sources=[]`、空の作業ディレクトリ。
2. **起動時のツール一覧の確認**: SDK が最初に流す初期化のメッセージのツール一覧に、5 個（`mcp__diag__…`）以外が
   1 つでもあれば、モデルにツールを使わせる前に中断する。
3. **途中の確認**: 5 個以外のツールの呼び出しが流れてきたら、その場で中断する。

中断したときは `failed`・`tool_isolation_failed` になり、診断結果は「不明」になる（提出が受理された後でも、中断が勝つ）。
警告のログ（`outside the custom tools` を含む行）に、見つかったツール名が出る。Slack への 2 通目は投稿しない。

**未確認の点**: 初期化のメッセージの実際の形（`subtype` が `init` で、一覧が `tools` に入ること）は、実物の CLI を
動かして確かめていない。形が違うと、2 の確認は素通りする（一覧が無い・list でないときは、確かめようがないので続行する）。
`strict_mcp_config=True` を渡しても、自分で定義したサーバーが今までどおり使えることも、実物では未確認である。

### 4.2 制約: 診断は、認証情報の書き戻しより前に走る

診断は `main.py` の `raise` と `finally` の前で走る。**診断の間は、Claude・Codex の認証情報の書き戻しが行われない。**

- ツールの呼び出しは、制限時間（既定 180 秒）を過ぎてから始まるものを断る（`deadline_exceeded`）。ただし、
  期限の前に始めた記録の読み取り、完了イベントの書き込み、Slack への投稿は、期限の外にある。
- そのため、書き戻しが遅れる長さは、制限時間では収まらない。最大で
  「制限時間 180 秒 ＋ SDK の終了待ち（子プロセスの後始末）＋ ツールのスレッドの終了待ち（`boto3` の接続 5 秒・
  読み取り 10 秒 × 試行 2 回が、呼び出しごとに）＋ 2 通目の Slack 投稿の再試行（最大 3 回）」ぶん、書き戻しが遅れる。
- その間にタスクが落ちる（メモリ不足、タスクの停止など）と、元の実行で更新されたトークンが書き戻されない。
- 診断役自身も、実行中にトークンを更新しうる。
- 書き戻しを診断の前に移すと、2 回目の書き戻しは「起動時から Secrets Manager の値が変わっている」ために飛ばされ、
  診断中の更新が失われる。どちらを取っても、失われうる更新がある。
- 診断の呼び出しが受けるのは `Exception` だけである。診断の中で `BaseException`（`KeyboardInterrupt`、`SystemExit` など）
  が上がると、元の例外を置き換えうる（書き戻しは `finally` で走る）。

コードは変えていない。**どちらを取るかは、本番で有効にする前にユーザーが決める。**

## 5. 上限

| 上限 | 既定値 |
|---|---|
| ターン数 | 15 |
| 全体の制限時間 | 180 秒 |
| ツール呼び出し総数（提出は数えない。検証に落ちた呼び出しは数える） | 20 |
| 診断結果の提出の試行（受理・不受理を問わない） | 5（設定では変えられない） |
| ツールの呼び出しを受け付ける期限 | 開始から制限時間（既定 180 秒）まで。過ぎてから始まる呼び出しは `deadline_exceeded`（提出を含む） |
| ツール結果の累計の大きさ（提出は数えない） | 200,000 バイト |
| ツール結果 1 回の大きさ | 20,000 バイト |
| 文字列項目 1 つの長さ | 800 字（先頭 300 字＋末尾 500 字を残す） |
| イベント 1 回の件数 | 30 |
| イベントの読み込み | 500 件、または合計 2MB まで（設定では変えられない。読み止めたら、結果の `truncated` が真になる） |
| 段階の読み込み | 200 件、または合計 2MB まで（同上。段階の `result` の本体は読まない） |
| 例外の型の許可一覧の走査 | `.py` ファイル 2,000 個、1 ファイル 1MB まで |
| プロンプト記録 1 件の大きさ | 1MB（超えたら `size_limit`） |

コードから呼ぶときは `diagnose_execution(execution_id, limits=DiagnosisLimits(...))` で変えられる。
SDK の呼び出しは 1 回だけで、再試行も上位モデルへの切り替えもしない。

## 6. 受け渡し用のファイルの作り方

第 2 段階（修正役）が受け取るのは、受け渡し用の診断結果（JSON、`schema_version: 1`）だけである。
中身は、決まった値・形を検証した実行 ID・コードが記録から取り出した例外の型とコードの場所・有効な根拠の件数・
「修正役に渡せる」の判定で、自由記述と記録の中身は含まない。

作り方は 2 通り。どちらも中身は同じ。

1. **手元で診断をやり直す**: `python -m diagnosis <execution_id> --handoff-out <path>`。
   診断が `completed` のときだけ書き出す。**書き出し先に既にファイルなど（ディレクトリ、先の無いシンボリックリンクを含む）が
   あると、診断を始める前に終了コード 2 で終わる**（古い受け渡しを、修正役が拾わないようにするため）。
   まだ無いパスを指定するか、古いファイルを自分で消してから実行する。
2. **本番の自動診断の結果から取り出す**: `diagnosis_completed` イベントの `payload.handoff` を、
   ダッシュボードの API か AWS のコンソールから取り出して保存する。

ファイルを作る場所（記録を読める権限のある環境）と、修正役が動く場所は別である。人がファイルを運ぶ。

## 7. 既知の制限

- **ECS ではプロンプト記録を読めない**。タスクロールは S3 の書き込み権限しか持たないため、`unavailable` になる。
- **既存の役（調査・生成・レビュー）の足取りは分からない**。どのツールをどの引数で呼んだかは記録されていない。
- **診断の当たり外れは自動テストでは分からない**。手動確認で見る。
- **段階の ID の形**。プロンプト記録の番号は英数字・ハイフン・下線（64 字まで）だけを受け付ける。
- **イベントは 500 件まで、合計 2MB まで**。それを超える実行は、先頭から読めたぶんだけで診断する。
- **コードの場所は `/app/` のフレームだけ**。ライブラリの中で起きた例外は、呼び出し元までしか渡らない。
- **コードの場所は、診断役が動いている環境のコードと突き合わせる**。版が違うと、本物のフレームも捨てられる。
  `<lambda>` や内包表記のフレームも捨てる。
- **コードの場所は、スタックトレースの最初のブロックからだけ取る**。次のものは取れない: CRLF の記録、先頭にログの行が
  ある記録、深い再帰（`[Previous line repeated …]` の後ろ）、5,000 字で切られた記録の末尾のフレーム、連鎖した例外の
  2 つ目以降のブロック。
- **記録そのものを直接書き換えられる相手には、最初のブロックの限定は効かない**（1 行目から偽のトレースを書ける。
  その場合も、実際のコードにある場所しか通らない）。根本策は、記録する側が構造化したフレームを残すことで、別の作業単位の候補。
- **許可一覧に無い依存ライブラリの例外は、例外の型が `None` になり、「修正役に渡せる」は偽になる**。
- **次の場合も、例外の型と場所が使えず、「修正役に渡せる」は偽になる**。
  - 連鎖した例外（`raise … from e`、`except` や `finally` の中で上がった別の例外）。内側と外側の型が同じでも渡らない。
    トレースの最初のブロックは内側の例外のもので、外側の例外の場所ではないためである。
  - 5,000 字以上のスタックトレース。記録が先頭 5,000 字で切られるので、後ろに連鎖があっても分からない。
  - スタックトレースを持たないイベント（`subagent_failed` など）を、例外の根拠に選んだ場合。
  - 例外の行の型が、記録された型と違うトレース。

  モデルに返す結果には、どの場合も、例外の型とフレームを今までどおり返す。
  根本策は、記録する側が、例外の型と構造化したフレームを組で残すことで、別の作業単位の候補。
- **受け渡しの「コードの場所」は、例外の根拠にしたイベントのフレームだけ**。並びはトレースに現れた順で、重複は無い。
  モデルが選べるのは、どのイベントを根拠にするかと、そのイベントのどのフレームを含めるかだけである。
  修正役は、場所の件数や並びに意味を持たせない。
- **子の CLI は、親の環境変数（AWS や Slack の認証情報を含む）を引き継ぐ**。組み込みツールが外れていれば害はないが、
  隔離はその一点に依存する（§4.1）。
- **「修正役に渡せる」は、モデルの申告に依存する**。コードが確かめているのは、例外・場所・根拠が同じイベントで
  つながっていることで、「コードの不具合かどうか」はモデルの申告である。モデルが記録の中の指示に誘導されれば、
  通常の失敗でも真になりうる。修正役の側の独立した確認と、人によるプルリクエストの確認が、後段の守りである。
- **段階は 200 件まで、合計 2MB まで**。
- **診断役の費用は、実行の合計に入らない**。`diagnosis_completed` にだけ残る。
- **未確認の SDK の挙動**: `tools=[]` の実際の効き方、`error_max_turns` のときの `is_error`、
  `max_budget_usd` の効き方、初期化のメッセージの形、`strict_mcp_config` の効き方。手動確認で確かめる（§8）。
- **自動起動がオンのとき、失敗した実行の ECS タスクは長く動き、その間は認証情報の書き戻しが行われない**（§4.2）。

## 8. 手動確認で見ること

実際の LLM と記録を使う確認は、ユーザーの承認を得てから行う。そのとき、次を確かめて記録する。

- **起動時のツールが、自分で定義した 5 個だけであること**。初期化のメッセージに `subtype: init` と `tools` の一覧があり、
  一覧が `mcp__diag__get_execution_overview`・`mcp__diag__list_steps`・`mcp__diag__list_events`・
  `mcp__diag__get_prompt_record`・`mcp__diag__submit_diagnosis` だけであること。それ以外があれば、診断は
  `tool_isolation_failed` で止まる。
- 初期化のメッセージの形が、上の想定（`subtype` が `init`、一覧が `tools`）と合っていること。合っていなければ、
  起動時の確認は効いていない。
- **一覧が欠けている・形が違う場合に素通りする現在の作りを、実物の形を確かめたうえで、失敗にするかを決める**
  （いまは、一覧が無い・list でないときは続行する）。
- `strict_mcp_config=True` を渡した状態で、5 個のツールが呼べること。
- `tools=[]` の実際の効き方、`error_max_turns` のときの `is_error`、`max_budget_usd` の効き方。
- 実際の `step_id` の形（プロンプト記録の番号として受け付けられるか）。
- 実際の失敗した実行で、スタックトレースのフレームが「コードの場所」として残ること（版が合っていること）。
- 診断結果・足取り・ターン数・所要時間の実際の出力。
