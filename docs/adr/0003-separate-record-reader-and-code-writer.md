# 実行の記録を読む役と、コードを書く役を分ける

失敗した実行を調べてコードを直す仕事を、実行診断役（`src/agent/diagnosis/`）と修正役（`src/fixer/`）の
2 つに分けた。実行の記録には、Web から取った文章など、信頼できない内容が入る。それを読むモデルに、
コードを書く手段を持たせないための分け方である。本 ADR は、この境界をどこに引き、何で守るかを記録する。

採用した決定は 4 点。

1. **読む役と書く役を分ける**。実行診断役は、読み取り専用のカスタムツール 5 個だけを持つ。修正役は、
   作業用の複製の中で読み書きするカスタムツール 7 個だけを持ち、記録の生の文面を受け取らない。
2. **2 つの役の間は、受け渡し用の診断結果だけでつなぐ**。中身は、決まった値と、コードが記録から取り出して
   実際のコードと突き合わせた識別子だけ。修正役はこれを信頼せず、形・コードの場所・例外の型・条件を検証し直す。
3. **修正の合否は、モデルの申告ではなく、コードが実際に実行して決める**。合否の検査 G1〜G10 をすべて通った
   変更だけを、作業用ブランチにコミットする。
4. **手元から自動では外に出さない**。プッシュ、プルリクエストの作成、main への取り込みは、人が行う。

## 前提となる事実

- どちらの役も Agent SDK の上で動く（ADR 0001 と矛盾しない）。組み込みツールは外し、モデルにはカスタムツール
  だけを使わせる。それ以外のツールが見えたら、中断する
- 受け渡しに、モデルが書いた文字列は入らない。モデルに残るのは選択だけである。決まった値のどれを選ぶか、
  どの例外のイベントを根拠にするか、そのイベントのどのフレームを含めるか
- 受け渡しは JSON ファイル 1 つで、人が運ぶ。実行診断役は記録を読める権限のある環境で動き、修正役は本番の
  認証情報がない環境で動く
- 合否の検査 G5〜G8 は、修正役が作業した複製ではなく、コードが組み立て直した検査用の複製で走る
- 修正役は本番のイメージに入らない。入口は手動実行だけである
- **実際の LLM と AWS の記録を使った動作は、どちらの役も未検証である**。自動テストが確かめているのは、
  ツール・上限・検証・照合・検査の経路で、診断が当たるか、修正役が実際に直せるかではない。SDK の挙動にも、
  実物で確かめていない点がある（`tools=[]` の効き方、起動時のツール一覧の形）

## Considered Options

- **1 つの役が、記録を読んでコードも書く** — 構成は単純で、エラーメッセージの文面も使えるので直せる範囲が広い。
  しかし、記録に仕込まれた指示が、書く手段を持つモデルにそのまま届く。却下
- **診断結果の要約やエラーメッセージの文面も、修正役に渡す** — 修正の手がかりは増えるが、記録の文字列が
  書く役に届く経路になる。自由記述は、形の検証では安全にできない。却下
- **モデルが例外の型やコードの場所を文字列で出し、コードが「記録にあるか」を確かめる** — 当初の要求定義の形。
  記録に仕込んだ文字列を、そのまま通せる。コードが記録から取り出して ID を振り、モデルは ID を選ぶ形に改めた
- **修正役に、組み込みの読み書きのツールを使わせる** — 自作が要らないが、組み込みツールを作業用の複製の中に
  確実に閉じ込める手段を確かめられなかった。却下
- **合否を、修正役の終了の申告か、修正役が自分で走らせたテストの結果で決める** — 検査の時間が要らないが、
  作業用の複製はモデルが書き換えられる場所であり、申告は確かめようがない。却下
- **検査を通ったら、自動でプッシュしてプルリクエストを作る** — 人の手間は減るが、修正役の環境にプッシュの
  認証情報を置くことになる。検査は偽られうるので、人の確認を外せない。却下

## 判断の核

境界は、引いただけでは守れなかった。レビューのたびに、境界を越える経路が実際に見つかり、再現された。
決定 2 と 3 の「信頼せずに確かめ直す」は、その結果として具体的になった。

**記録の文字列が、書く役に届く経路**（実行診断役のレビュー、3 巡）。

- 例外メッセージの中の、フレームの形をした文字列が、コードの場所として受け渡しに入った。フレームは、
  スタックトレースの最初のブロックからだけ取り、実際のコードにその関数・その行があるものだけを残す形にした
- イベントの例外の型の欄に入れた任意の文字列が、そのまま受け渡しに入った。コード側の許可一覧にある名前だけを
  通す形にした
- 連鎖した例外で、内側の例外の場所と、外側の例外の型が組になった。場所の選び方・並び・重複もモデルに残っていた。
  例外の型は、最初のブロックを終える行の型と一致するときだけ使い、場所は、その例外のイベントのフレームだけを、
  トレースに現れた順で入れる形にした

3 巡目の再レビューで、受け渡しに自由な文字列が入る経路は残っていない、と確かめられた。3 つ目の項目は、
その 3 巡目で見つかった指摘で、直した後の再レビューの記録は無い。

**修正役が書いたテストが、検査やコミットをだます経路**（修正役のレビュー、2 巡）。

- 新しいテストが、隣に置かれた検査用の複製を正しい実装に書き換え、壊れた修正が検査を通った。検査用の複製は、
  使う実行の直前に 1 つずつ作り、前後で中身を照合する形にした
- 新しいテストが、元のリポジトリにフックを置き、修正役の git がそれを実行した。git は、フック・fsmonitor・
  全体設定を無効にして呼び、`.git` の設定とフックが変わっていたらコミットしない形にした
- 新しいテストが、検査に使う Python の環境にコードを仕込めた。置換参照で、コミットに検査していない変更を
  入れられた。フィルターの設定で、複製を作る git に任意のコマンドを走らせられた。それぞれ、起動の前の確かめ、
  作ったツリーと基準の記録との照合、モデルが書いたコードが走った後は `git archive` を呼ばない作りで塞いだ

どれも、決定 3 の「コードが実際に実行する」ことから生じる。モデルが書いたコードを走らせる以上、そのコードは
検査の仕組みそのものに手を出せる。見つかった経路は塞いだが、同じ種類の経路が残っていないとは言えない。
決定 4 は、そのための最後の守りである。

## Consequences

受け入れた不便。

- **直せる範囲が狭い**。修正役は、エラーメッセージの文面を受け取らない。既存のテスト、`conftest.py`、設定、
  依存の定義、認証に関わるコード、実行診断役と修正役のコードは、対象外の場所で、直せない。まだ無い関数や
  モジュールを足す種類の修正も、成果物にならない（再現テストが、修正前に集めるときのエラーになるため）
- **修正役に渡らない診断が多い**。許可一覧に無い依存ライブラリの例外、連鎖した例外、スタックトレースを
  持たないイベント、失敗した実行と版が違うコードでは、「修正役に渡せる」の判定が偽になるか、修正役が起動しない
- **読み書きのツールを自作し、保つ手間がかかる**。検査 1 回は、このリポジトリで 5〜6 分かかる
- **人の手が要る**。受け渡しのファイルを運ぶ、差分と再現テストを読む、プッシュする、プルリクエストを作る

残っている限界。この決定だけでは防げない。

- **修正役が書いたテストは、起動した人の権限で、通信を含む任意のコードとして動く**。カスタムツールの縛りは、
  テストのコードには効かない。環境変数とホームの絞り込み、起動の前の確かめは、歯止めであって隔離ではない
- **修正役は、隔離した環境で試しに動かせる段階である**。使い捨てのコンテナか専用の利用者で、本番の認証情報が
  ない環境で動かす。ふだんの開発の環境で使えるものではない。条件は `docs/execution-fixer.md` §2.1 にある
- **修正役の最後の修正は、再レビューを受けていない**
- **合否の検査は、修正されたコードに偽られうる**。成否は、テスト対象のプロセスが書ける結果のファイルと
  終了コードから読む。検査が確かめるのは「新しいテストが、この変更で、落ちる状態から通る状態になった」ことと
  「既存のテストの結果が変わらない」ことだけで、再現テストが実際の失敗と同じ原因を突いているかは見ていない
- **「修正役に渡せる」の判定は、実行診断役のモデルの申告に依存する**。コードが確かめるのは、例外・場所・根拠が
  同じイベントでつながっていることだけである。記録そのものを書き換えられる相手は、偽のコードの場所を
  受け渡しに入れられる。その場合も、入るのは実際のコードにある場所だけで、修正役にとって場所は手がかりにすぎない
- **役の隔離は、組み込みツールが実際に外れていることに依存する**。子の CLI は、親の環境変数を引き継ぐ

後続の作業。

- 根本の対応は、テストの実行を、通信もファイルも遮断した実行環境に移すことである。設計の変更になるので、
  別の作業単位とする。それまでは、動かす環境の側で隔離する
- 記録する側が、例外の型と構造化したフレームを組で残せば、コードの場所を文字列のトレースから取らずに済む。
  これも別の作業単位の候補である
- 実際の LLM と記録を使う確認は、未実施である。見る点は、2 つの使い方の文書（`docs/execution-diagnostician.md` §8、
  `docs/execution-fixer.md` §10）にある
