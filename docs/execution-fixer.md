# 修正役（第 2 段階）の使い方

> 「修正役」「受け渡し用の診断結果」「合否の検査」は、正式な名称として確定し、`docs/glossary.md` に登録済み（2026-10-05）。
> 設計は `.steering/20261004-execution-fixer/design.md`、受け入れ条件は同 `requirements.md`。
> **実際の LLM を使った動作は未検証**（任意条件 O1。実施にはユーザーの承認が要る）。
> 自動テストが確かめているのは、入力の検証・縛り・合否の検査・成果物の出し方であり、修正役が実際に直せるかどうかではない。
> **位置づけ: 隔離された環境で、試験的に動かせる段階。ふだんの開発の環境で使えるものではない**（§2.1）。

## 1. 何をするものか

実行診断役（第 1 段階。`docs/execution-diagnostician.md`）が出した**受け渡し用の診断結果**を 1 つ受け取り、
リポジトリの複製の中で、失敗を再現するテストと修正を作る。コードによる**合否の検査**にすべて通ったものだけを、
手元の作業用ブランチにコミットし、プルリクエスト本文の下書きを添える。

- 受け取るのは、固定項目だけの JSON ファイル。修正役はこれを信頼せず、形・コードの場所・例外の型・条件を検証し直す。
  診断役の自由記述と、実行記録の中身（エラーメッセージの文面を含む）は受け取らない。
- 作業は、基準のコミットを書き出した複製（`.git` の無い一時ディレクトリ）の中だけで行う。
- モデルが使えるのは、自分で定義した 7 個のツール（一覧・読み取り・検索・書き込み・置き換え・テスト実行・終了の申告）だけ。
  シェル・通信・git は使えない。それ以外のツールが見えたら、中断する。
- 書けるのは `src/` と `tests/` の下の `.py` だけ。既存のテスト、`conftest.py`、設定、依存の定義、
  認証に関わるファイル（`src/agent/main.py` など）、診断役と修正役のコードそのものには書けない。
- 成果物として認めるかどうかは、モデルの申告ではなく、コードが組み立て直したきれいな複製で、実際にテストとリントを走らせて決める。
- **プッシュ、プルリクエストの作成、main への取り込みは行わない**。人が行う（§5・§6）。
- 元のリポジトリの作業ツリー・現在のブランチ・インデックスには触れない。増えるのは、ブランチ 1 つと、そのコミットだけ。
  git は、フック・fsmonitor・全体設定を無効にして呼ぶ。
- **修正役が書いたテストは、起動した人の権限で、任意のコードとして走る**。使い捨てのコンテナか、専用のユーザーで動かすこと（§2.1）。

実装は `src/fixer/`（本番のイメージには入らない）。入口は、手動実行の 1 つだけ。

## 2. 手動実行の手順

pytest の既定実行では走らない。次の手順で、人が 1 回ずつ動かす。

### 2.1 前提

**修正役が書いたテストは、起動した人の権限で、通信を含む任意のコードとして走る。** 元のリポジトリの `.git`、
開発用の仮想環境、シェルの設定にも書ける。複製の外のファイルを読んで、テストの出力としてモデルに返すこともできる。
テストに渡す環境変数の `HOME` は差し替えてあるが、本物のホームは分かる。コードでは塞げないので、**動かす環境の側で隔離する**。

**位置づけ**: 修正役は、「隔離された環境で、試験的に動かせる段階」であり、ふだんの開発の環境で使えるものではない。
レビューを重ねるたびに、「修正役が書いたテストのコードが、修正役自身の処理（検査、コミット、後始末）を騙す・踏み台にする」
経路が見つかっている（1 巡目: 検査用の複製の書き換え、フックの実行。2 巡目: 仮想環境への書き込み、置換参照、フィルター）。
見つかったものは塞いだが、**この種の経路が残っていないとは言えない**（最後の修正は、再レビューを受けていない）。
根本の解決は、テストの実行を、通信もファイルも遮断した実行環境（サンドボックス）に移す設計の変更で、別の作業単位である。

| 前提 | 内容 |
|---|---|
| **隔離された環境** | 使い捨てのコンテナか、専用のユーザーで動かす。開発者のふだんのシェルでは動かさない |
| **検査に使う Python の環境に、書き込めない** | 仮想環境（`.venv`）と Python 本体を、テストを走らせる利用者から書き込めない所有者にする。コンテナなら、環境は root の所有にし、修正役の実行は別の利用者で行う。**同じ利用者のまま読み取り専用にするだけでは足りない**（テストのコードが、権限を戻せる）。書き込めると、テストのコードが、以後の検査をすべて偽れる（仕掛けは、提案の差分に現れない） |
| **リポジトリは複製を使う** | ふだん使っている作業ツリーではなく、`git clone` した複製を `--repo` に渡す（テストのコードは、元のリポジトリの `.git` に書ける）。**部分クローンでない、完全な複製**を使う |
| **本番の認証情報がない環境** | AWS のプロファイル、GitHub のトークン、プッシュの認証情報、`~/.ssh`、`~/.aws` を置かない |
| サブスクリプション認証 | Claude Code にログイン済みであること（`claude login`）。API キーは使わない。手順は `docs/credential-setup.md` §4。**この認証（`~/.claude`）は、同じ環境に必ず要るので、テストのコードから読まれうる**。隔離した環境には、修正役のためだけの認証を置く |
| Python の依存 | 開発用の仮想環境（`.venv`）。検査のテストとリントは、修正役を動かしている Python で走る |
| 作業ディレクトリ | リポジトリの根。`PYTHONPATH=src/agent` を付ける（第 1 段階のコードを再利用するため） |
| 出力先 | リポジトリの外で、まだ無いか、空のディレクトリ |

うっかりを防ぐ歯止めとして、起動した利用者の本物のホームに、`.aws`・`.ssh`・`.netrc`・`.git-credentials`・`.config/gh`・
`.docker/config.json`・`.codex`・`.kube`・`.gnupg` のどれかがあると、修正役は何もせずに `failed`・`unisolated_environment` で終わる
（見つけたものの名前だけを、ログに出す。中身は読まない）。検査に使う Python の環境（`sys.prefix` と site-packages）が、
いまの利用者から書き込めるときも、同じく `failed`・`unisolated_environment` で終わる（見つけたパスを、ログに出す。何も書かない）。
開発者のふだんの仮想環境は、ふつう書き込めるので、そのままでは起動しない。分かったうえで動かすときだけ、`--allow-unisolated` を付ける
（**両方の確かめを飛ばす**）。どちらも歯止めであって、隔離の代わりではない（見ているのは、上の 2 か所の権限だけである）。

### 2.2 環境変数

| 環境変数 | 必須 | 内容 |
|---|:---:|---|
| `PYTHONPATH=src/agent` | o | 第 1 段階のコード（`diagnosis`）を読み込むため |
| `FIXER_MODEL` | | モデル名。未設定なら `sonnet` |

### 2.3 受け渡し用のファイルの作り方

第 1 段階の手動実行で、`--handoff-out` を付けて書き出す（`docs/execution-diagnostician.md` §6）。

```bash
cd src/agent
python -m diagnosis <execution_id> --handoff-out /path/outside/repo/handoff.json
```

修正役が起動するのは、次をすべて満たす受け渡しだけである。満たさなければ、SDK を呼ばずに `not_eligible` で終わる。

- 「修正役に渡せる」が真で、原因の性質がコードの不具合、確からしさが高、推奨する対処が「コードの修正」、
  原因の分類が「不明」「記録の不足」でなく、有効な根拠が 1 件以上
- 例外の型が、許可一覧（組み込みの例外、複製の `src/` の下のコードで定義されたクラス、依存ライブラリの決まった一覧）にある
- コードの場所が、複製のコードに実在し（ファイル・関数定義・その範囲内の行番号）、対象外の場所でないものが 1 件以上

### 2.4 実行例

```bash
PYTHONPATH=src/agent .venv/bin/python -m src.fixer \
  --handoff /path/outside/repo/handoff.json \
  --out-dir /path/outside/repo/fix-001
```

| 引数 | 必須 | 内容 |
|---|:---:|---|
| `--handoff` | o | 受け渡し用の診断結果のファイル |
| `--out-dir` | o | 結果・足取り・下書きの出力先 |
| `--base` | | 基準のコミット（既定は `HEAD`）。失敗した実行に載っていたコミットを指定すると、行番号がずれない |
| `--repo` | | リポジトリの根（既定はカレントディレクトリ） |
| `--allow-unisolated` | | ホームに認証情報らしいものがある環境、検査に使う Python の環境に書き込める環境でも起動する（既定では断る。2 つの確かめを、どちらも飛ばす。§2.1） |

終了コードは、`proposed` なら 0、それ以外の結果は 1、引数の誤りは 2。

## 3. 出力の読み方

標準出力に、終了理由・ブランチ名・検査の結果・出力先が出る。元のリポジトリの `.git/hooks` または `.git/config` が、
実行の間に変わっていたときは、標準エラーに注意が出る（`result.json` の `repository_changed` が真になる。§9）。出力先には、次のファイルができる
（起動の前の確かめに落ちたときは、何も書かない）。

| ファイル | 中身 | 書かれるとき |
|---|---|---|
| `result.json` | 結果の全体（終了理由、ブランチ、コミット、検査の結果、足取り、モデルの説明） | 起動の前の確かめを通ったとき |
| `trace.json` | 足取り（呼んだツール、対象のパス、結果の分類、所要時間、テスト実行の件数） | 同上 |
| `pr-draft.md` | プルリクエスト本文の下書き | `proposed` と `rejected` のとき |

### 3.1 終了理由

| `status` | `stop_detail` | 意味 |
|---|---|---|
| `proposed` | `committed` | 検査にすべて通り、作業用ブランチ `fix/diagnosed-<実行 ID>` にコミットした |
| `rejected` | `G5`、`G1+G2` など | 合否の検査のどれかに落ちた。変更は破棄した（`pr-draft.md` に、どの検査で落ちたかが出る） |
| `declined` | `no_changes` / `declined_with_changes` | 修正役が「直せない」と返した、または変更が無い。正当な結果 |
| `incomplete` | `max_turns` / `max_budget` / `timeout` / `no_finish` | 上限に達した、または終了の申告なしに変更だけが残った。変更は破棄した |
| `not_eligible` | `unknown_exception_type` / `no_verified_location` / `conditions_not_met` | 受け渡しが条件を満たさない。SDK は呼んでいない |
| `failed` | `unisolated_environment` | ホームに認証情報らしいものがある、または、検査に使う Python の環境に書き込める（§2.1）。何もしていない。出力先には何も書かない |
| `failed` | `not_a_repository` / `base_not_found` / `invalid_out_dir` / `branch_exists` | 起動の前の確かめに落ちた。出力先には何も書かない |
| `failed` | `unsupported_attributes` | 基準のコミットが `.gitattributes` の `export-ignore`・`export-subst` を使っている（複製の中身が、コミットの中身と食い違う）、または、1,000,000 バイトを超える `.gitattributes` がある。出力先には何も書かない |
| `failed` | `repository_tampered` | 元のリポジトリの `.git/hooks`・`.git/config`・`.git/info/attributes` が、実行の間に変わった（モデルの作業の後と、コミットの直前に照合する）。検査の前に気づいたときは、検査も走らせていない。コミットはしていない。**次の git の操作の前に、`.git/hooks` と `.git/config` を確かめること** |
| `failed` | `workspace_tampered` | 作業用の複製の根が、実行の間に、リンクや別のディレクトリに替えられた。変更を取り出さず、何も提案していない |
| `failed` | `invalid_handoff` | 受け渡しの形が合わない（未定義の項目、決まった値以外、識別子の形でない値など） |
| `failed` | `setup_error` / `tool_isolation_failed` / `sdk_error` / `commit_error` / `internal_error` | 準備・SDK・コミットの失敗、7 個以外のツールの検出 |

### 3.2 合否の検査

| 検査 | 通る条件 |
|---|---|
| G1 範囲 | 変更が、すべて `src/` または `tests/` の下にある。削除がない。パスの各要素に、ピリオドがない（最後の要素の、末尾の `.py` を除く） |
| G2 禁止の場所 | 対象外の場所（インフラの定義、CI、規律の文書、依存の定義、認証に関わるコード、診断役と修正役のコード、`src/trigger/app.py`）への変更がない。`src/` の下の既にある `__init__.py` に変更がなく、新しく足したものは空である。標準ライブラリ・依存パッケージ（決まった一覧と、基準のコミットの `requirements*.txt` に書かれたもの）・ほかのモジュールと同じ名前を、`src/` とその直下のディレクトリの直下に足していない |
| G3 既存のテスト | `tests/` の既存のファイルに変更・削除がない。足したのは、新しいテストファイルと空の `__init__.py` だけ |
| G4 再現テストがある | 新しいテストファイルが 1 件以上ある |
| G5 修正前に落ちる | 基準のコミットに新しいテストだけを足した複製で、新しいテストが、テストの失敗として落ちる（終了コード 1）。集めるときのエラー（まだ無いものを import するだけ、など）は認めない |
| G6 修正後に通る | 修正を足した複製で、新しいテストがすべて通り、修正前に落ちたテストが、すべて通っている |
| G7 ほかを壊さない | 既存のテストだけを走らせた結果（テストごとの成否と終了コード）が、基準と、修正後とで同じ。どちらも、結果が 1 件以上あり、終了コードが 0 か 1 |
| G8 リント | `ruff check` の指摘の数が、基準より増えていない |
| G9 大きさ | 変更したファイルの数と行数が上限以内（既定は 5 ファイル、200 行） |
| G10 差分の中身 | シンボリックリンク・モードの変化・バイナリ・`.py` 以外・秘密情報らしい文字列・双方向の制御文字・見えない文字・CR がない |

G5〜G8 は、修正役が作業した複製ではなく、コードが組み立て直した複製（基準のコミット＋検査を通ったファイルだけ）で走る。
複製は、使う実行の直前に 1 つずつ作り、終わったら消す（git は呼ばず、作業用の複製を作ったときの書き出しから組み立てる）。
順は、リント（基準・修正後）と、基準での既存のテストを先に、
モデルが書いたコードが動く実行（新しいテスト、修正後の既存のテスト）を後にする。各実行の前後で、複製の中身を照合し、
書き換えられていたら、その検査を不合格にする。テストの結果に、同じ ID のものが複数あった実行は、「検査できなかった」として、
その検査を不合格にする。

**所要時間**: このリポジトリでは、テスト一式が 1 回 2 分半ほどかかり、基準と修正後で 2 回走るので、検査 1 回は 5〜6 分になる。
検査の合計の上限は 15 分（`gate_timeout_seconds`）で、超えたら、残りの検査は不合格になる（リントにも、残り時間を渡す）。

## 4. 成果物の確認

`proposed` で終わったら、取り込む前に、次を人が確かめる。

1. `pr-draft.md` を読む。「修正役の説明」はモデルが書いたもので、未検証である。
2. 差分を読む: `git diff <基準のコミット> fix/diagnosed-<実行 ID>`
3. **再現テストが、実際に起きた失敗と同じ原因を突いているか**を確かめる。自動の検査が確かめたのは、
   「新しいテストが、この変更で、落ちる状態から通る状態になった」「既存のテストの結果が変わらない」ことだけである。
4. 診断の場所は手がかりにすぎない。修正が、失敗と無関係な場所に当たっていないかを見る。
5. トークンを受け取るファイル（`src/agent/storage/github_client.py`・`notion_client.py`、`src/agent/notify/slack_client.py`）を
   変えた成果物では、下書きの冒頭に「認証情報を扱うファイル」の注意書きが入る。トークンの受け渡し・送信先・ログへの出力が
   変わっていないかを、差分で確かめる。

## 5. 人が行う 2 コマンド（プッシュと PR の作成）

修正役は、プッシュも PR の作成も行わない。内容を確かめた後で、人が行う。

```bash
git push origin fix/diagnosed-<実行 ID>
gh pr create --head fix/diagnosed-<実行 ID> --body-file /path/outside/repo/fix-001/pr-draft.md
```

## 6. 取り込む前に、規律どおり行うこと

修正役の成果物は「提案」であり、`CLAUDE.md` の作業規律は変わらない。

1. `.steering/` に作業単位のドキュメント（requirements・design・tasklist）を起こし、承認を得る。
   修正役の下書きと再現テストは、その材料として使う。
2. プッシュの後、`CLAUDE.md` 作業規律 §4 の Codex レビューを通す。
3. main への取り込みは、人が行う。

## 7. 不要になったブランチの消し方

`rejected` などでは、ブランチは作られない。`proposed` で作られたブランチが不要になったら、人が消す。

```bash
git branch -D fix/diagnosed-<実行 ID>
```

同じ実行 ID でやり直すときも、先にこのブランチを消す（同じ名前のブランチが既にあると、修正役は `branch_exists` で終わる）。

## 8. 上限

| 上限 | 既定値 |
|---|---|
| ターン数 | 30 |
| 全体の制限時間 | 20 分（過ぎてから始まるツールの呼び出しは、何もせずに `deadline_exceeded` を返す） |
| 検査の合計の制限時間 | 15 分 |
| ツールの呼び出し（テスト実行と終了の申告を除く。検証に落ちた呼び出しも数える） | 120 回 |
| テスト実行 | 10 回（1 回の制限時間は 5 分。検査のテスト実行も同じ制限時間） |
| 終了の申告 | 5 回 |
| 1 回の読み取り | 60,000 バイト |
| ファイル 1 つの書き込み | 200,000 バイト |
| テスト 1 回の出力 | 5,000 万バイト（超えたら、実行を止める） |
| 変更したファイルの数と行数（G9） | 5 ファイル、200 行 |
| モデルの説明 | 800 字 |

手動実行の入口は、既定値で動かす。値を変えるときは、`run_fix` に `FixLimits` を渡す。

## 9. 既知の制限

- **隔離された環境で、試験的に動かせる段階である**（§2.1 の位置づけ）。修正役が書いたテストのコードが、修正役自身の処理を
  騙す・踏み台にする経路は、見つかるたびに塞いできたが、残っていないとは言えない。
- **修正役が書いたテストは、起動した人の権限で、通信を含む任意のコードとして走る**（§2.1）。環境変数とホームの絞り込みは、
  緩和であって隔離ではない。読み書きのツールの縛りは、テストのコードには効かない。テストのプロセスが残した子プロセスは、
  実行のたびにグループごと止めるが、`setsid` でグループを抜けたプロセスには効かない。**本番の認証情報がない、隔離された環境で動かす**こと。
- **元のリポジトリに置かれたフック・設定は、残る**。修正役は、置かれたフックを実行せず、`.git/hooks`・`.git/config` が
  変わっていたらコミットしない（`repository_tampered`）。しかし、置かれたものを消しはしない。`repository_tampered` や、
  終わりの注意（`repository_changed`）が出たら、**`.git/hooks` と `.git/config` を確かめてから、次の git の操作をする**こと
  （人がふつうに `git commit` すれば、置かれたフックが走る）。
- **合否の検査は、修正されたコードに偽られうる**。検査は、テスト対象のプロセスが書ける JUnit の XML と、
  終了コードから成否を読む。修正されたコードは、そのプロセスの中で動くので、結果を偽れる。
  検査用の複製は、実行ごとに作り直して照合するが、`setsid` で残ったプロセスが、次の複製を待ち伏せして書き換え、
  照合の前に戻す競合は防げない。最後の守りは、人によるプルリクエストの確認である。
- **置かれた置換参照（`refs/replace/`）や、フィルターの設定も、残る**。修正役の git は、置換参照を読まず、モデルが書いた
  コードが走った後は `git archive` を呼ばず、コミットを作るときは、作ったツリーを、実行の最初に取った基準の記録と比べる。
  しかし、人がふつうに使う git は、置換参照を読む。照合の対象に、`refs/replace/` は入っていない。
- **「本体で失敗し、後始末でもエラー」のテストが 1 件でもあると、提案できない**。pytest が、同じ ID の結果を 2 つ書くためである
  （同じ ID の結果が複数ある実行は、「検査できなかった」として扱う。安全な側の割り切り）。
- **独立した確認（G5・G6）は、無関係な「落ちるテスト」と、それを通すだけの変更を見分けられない**。
  検査が確かめるのは「このテストが、この変更で、落ちる状態から通る状態になった」ことだけである。
- **まだ無い関数やモジュールを足す種類の修正は、成果物にならない**。新しいテストが、修正の前に、集めるときのエラーになるためである（G5）。
- **G7 は、成否が「同じ」であることを求める**。基準の時点で落ちていたテストは、落ちたままなら妨げにならないが、
  修正でそのテストが通るようになった場合も不合格になる（安全な側に倒している）。その修正は、人が取り込む。
- **既存のテスト 2 件（`TestCallClaudeWithWorkspace` の 2 件）は、検査の実行では落ちる**。テストに渡す `TMPDIR` が
  `/tmp/fixer-run-*/tmp` になるためである。基準と修正後で同じように落ちるので G7 は通るが、この 2 件は、修正で壊れても検出されない。
- **場所は手がかりにすぎない**。記録そのものを書き換えられる相手は、偽の場所を受け渡しに入れられる。
  誤った場所を指されたとき、修正役は「直せない」と返すか、無関係な修正案を出す。
- **版のずれ**。基準のコミットが、失敗した実行の版と違うと、場所の行番号が関数の範囲から外れて捨てられる
  （`not_eligible`）。`--base` で、失敗した実行に載っていたコミットを指定できる。
- **直せる範囲が狭い**。エラーメッセージの文面を渡さない。既存のテスト・`conftest.py`・設定を変える必要がある修正、
  `src/agent/main.py`・`src/trigger/app.py`・認証まわり・診断役・修正役自身の修正、既にある `__init__.py` の変更、
  実行権限のあるファイルの修正は、対象外。標準ライブラリなどと同じ名前のモジュールは、足せない。
  パスの要素に、ピリオドは使えない（末尾の `.py` を除く）。
- **依存の名前の一覧の限界**。足せない名前は、決まった一覧と、基準のコミットの `requirements*.txt` の配布物の名前から作る。
  配布物の名前と import の名前が違うもの（`PyYAML` → `yaml` など）は、決まった一覧にあるものしか拾えない。
- **`export-ignore`・`export-subst` を使うリポジトリは、扱わない**（`unsupported_attributes`）。1,000,000 バイトを超える
  `.gitattributes` があるコミットも、扱わない。`.git/info/attributes` は、先頭の 1,000,000 バイトだけを見る。
- **開発用の環境に依存する**。検査のテストは、修正役を動かしている Python と、その依存で走る。
- **リントの比べ方は件数だけ**。指摘が 1 件減って 1 件増えた場合は通る。
- **SDK の未確認の点**（`tools=[]` で組み込みツールがすべて外れるか、初期化のメッセージにツール一覧が入るか）は、
  実際に動かすまで分からない。どちらでも壊れない作りにしてある。手動確認のときに確かめる。
