## レビュー観点 (優先順)

- P1 本番のイメージに入るもの: `src/agent/diagnosis/` と `src/agent/main.py` の変更
  - フラグがオフのとき、既存の動作が少しでも変わらないか (import の副作用、例外の流れ、終了コードを含む)
  - フラグがオンのとき、診断の失敗、例外、遅れ、ハングが、
    元の失敗の通知 (`_notify_task_failure`) と、finally 節での認証情報の書き戻し
    (`_writeback_claude_credentials` など) を妨げないか。
    診断全体の期限が、スレッド・サブプロセス・イベントループのどの形のハングにも実際に効くか。
    ECS タスクの停止までの時間との関係で、書き戻しが打ち切られる形は無いか
  - 診断役が認証情報のファイルを変えた場合 (トークンの更新など) の、書き戻しとの整合
  - Slack の投稿文に、マスクされていない秘密情報、メンション、リンク、書式の注入が残らないか
- P2 上の A と B。直し方に誤りや抜けが無いか。直したことで、別の問題が入っていないか
  - A: マスクの正規表現の見落としと過剰な一致、破滅的なバックトラック。
    場所の選び方と、連鎖した例外 (`__cause__` / `__context__`) の扱いの正しさ
  - B: 作業用の複製からの脱出 (シンボリックリンク、`..`、絶対パス、git の置換参照・
    フック・設定・属性・サブモジュール・代替オブジェクト)、検査用の複製の独立性、
    対象外の名前の判定の抜け、テスト結果の読み取りの偽陽性・偽陰性
    (失敗を合格と読む形が無いか)、後始末の漏れ (一時ディレクトリ、ブランチ、作業ツリー、
    子プロセス)、大きなファイルでの資源の使い過ぎ
- P3 ADR-0003 と 2 つの設計書の「既知の制限」に書かれていない問題。
  既知の制限として書かれているものは、指摘に数えなくてよい。
  ただし、書き方が実態より控えめなら、それは指摘する
- P4 そのほか: 正しさ、資源の後始末、テストの弱点
  (実装をなぞるだけのテスト、偽物に頼りすぎて実物の挙動を確かめていないテスト、抜けている境界)

## 進め方と制約

- 読み取り専用で調べる。ファイルを書き換えない。コミット、プッシュ、`git stash`、
  ブランチの作成や切り替えなど、リポジトリの状態を変える操作をしない
- この作業ディレクトリの外のファイルを読まない。ホームディレクトリの下の
  秘密のファイル (SSH 鍵、AWS・Claude・Codex の設定、個人のデータ) を読まない
- ネットワーク、AWS、Slack、LLM を呼ばない
- 差分は大きい (86 ファイル、約 38,700 行。うちテストが約 27,000 行)。
  `git diff main..HEAD --stat` で全体をつかみ、まず `src/agent/main.py` と
  `src/agent/diagnosis/` を全部読み、次に `src/fixer/` を読み、
  テストは指摘の裏付けに要る所だけ読む、という順を勧める
- 推測で指摘しない。指摘ごとに、ファイルと行、問題が起きる具体的な入力か手順を示す。
  コードを読んで確かめられなかったものは「未確認」と明記する

## 期待する出力

日本語で、次の形で報告する。

1. 結論: 指摘はゼロか。main に入れてよいか
2. 指摘の一覧。1 件ごとに次を書く
   - 重大度: P0 (main に入れてはいけない) / P1 (入れる前に直す) / P2 (直すべきだが入れてよい) / P3 (提案)
   - 区分: 本番のイメージに入る / 修正役だけ / 文書だけ / テストだけ
   - 場所: ファイルと行
   - 内容と、問題が起きる具体的な入力か手順
   - 既知の制限に書かれているか: 書かれていない / 書かれている (どの文書のどの節) /
     書かれているが実態より控えめ
   - 直し方の案
3. 観点 P1〜P4 ごとに、問題なしと判断した点とその根拠
4. 読んだ範囲と、読めなかった範囲
