> 状態: **承認済み（2026-10-04）**。承認の記録は §6 の末尾。設計で変えた点は `design.md` §16 にあり、本ファイルにも反映済み。

> 経緯: 同日の別案（出典 URL の実在確認、`.steering/20261004-custom-tool-source-verifier/`）は保留。方式（既存の Claude Agent SDK のまま、カスタムツールを自分で定義する）は同じで、題材を実行の診断に変えた。

## 1. 背景・問題

本システムは、各エージェントの実行を後から調べられるよう記録を残している。

| 記録 | 場所 | 中身 |
|---|---|---|
| イベント | DynamoDB events テーブル（`src/observability/event_emitter.py`） | `topic_received` / `workflow_planned` / `subagent_started` / `subagent_completed` / `subagent_failed` / `research_completed` / `api_call_completed` / `rate_limit_hit` / `review_completed` / `error` / `execution_completed` など。失敗時の `error_type`・`error_message`・`stack_trace` はここに入る |
| プロンプトと出力の全文 | S3 `prompts/{execution_id}/{subagent}_{index}.json`（`src/observability/prompt_recorder.py`） | researcher / generator_text / generator_code / reviewer_eval / reviewer_fix |
| 実行と段階の状態 | DynamoDB workflow-executions / workflow-steps | 状態と時刻、トークン・費用の合計 |

しかし、次の 3 点が足りない。

1. **記録を読むのは人だけ**。ダッシュボード用の API 以外に、記録を読み返して使う処理がない。失敗時の Slack 通知は例外の型で文面を出し分けるだけで、多くは「ログを確認しますのでお知らせください」で終わる（`src/agent/main.py:194-277`）。
2. **自分で定義したツールがない**。使っているのは SDK 組み込みのツールと、レビュアーが打つ `curl` だけ。
3. **モデルが「次に何をするか」を決める範囲が狭い**。オーケストレーターは順番が固定のプログラムで、各呼び出しにターン数などの上限も指定していない。

## 2. 変更・追加する機能

既存の Claude Agent SDK を使ったまま、**実行診断役**を追加する。実行 ID を 1 つ受け取り、その実行の記録を**自分で選んで調べ**、固定の構造の診断結果を返す。

- 記録を読むためのツールは、すべて自分で定義する読み取り専用のカスタムツール（SDK のインプロセス MCP サーバー）。
- どの記録を、どの順で、どこまで読むかはモデルが決める。読める範囲・上限・診断結果の検証はコードが握る。
- 診断役が行うのは「調べる」と「対処を提案する」まで。コードを「直す」のは第 2 段階の修正役である。

### 全体の中での位置づけ（二段構え）

ユーザーの要望は「エージェントが自律してデバッグできるようにする。『直す』までやる」である。これを 2 つの役に分け、**権限を分離**する。本ファイルは第 1 段階を扱う。

| 段階 | 役 | 読むもの | できること | 作業単位 |
|---|---|---|---|---|
| 第 1 段階 | **実行診断役** | 実行記録（信頼できない内容を含む） | 読み取りだけ。診断結果を返す | 本ファイル |
| 第 2 段階 | **修正役** | コードが検証した固定項目の診断結果と、リポジトリの複製 | 複製の中でコードを直し、テストを走らせ、作業用ブランチにコミットする | `.steering/20261004-execution-fixer/requirements.md` |

分ける理由: 実行記録には Web から取った文章・プロンプト・生成物が入っており、指示文が仕込まれうる。それを読む役にはコードを書き換える力を持たせず、コードを書き換える役には記録の生の文面を渡さない。両者をつなぐのは、決まった値と検証済みの識別子だけからなる**受け渡し用の診断結果**（§4.2 R12a）である。

第 1 段階は単独で価値がある（失敗の原因と対処の提案が Slack に届く）。第 2 段階が遅れても使える。

**「直す」に含めないもの**（どちらの段階でも行わない）: 本番の実行の自動やり直し、main への直接の取り込み、デプロイ。やり直しは「再投入を勧める」提案にとどめる。途中から再開する仕組みがなく、Slack への二重投稿と費用の重複が起き、タスクの起動権限の追加（`template.yaml` の変更）も要るためである。

### 確認が必要な決定（推奨つき）

| # | 決める点 | 選択肢 | 推奨と理由 |
|---|---|---|---|
| D1 | 作業単位の分け方 | 診断役と修正役を **2 つの作業単位に分ける** ／ 1 つにまとめる | **分ける**。権限も動く場所も違い、第 1 段階だけで完成・検証できる。過去の作業単位も 1 つの目的ごとに切られている。規模も合計で 20 時間前後になり、1 つでは承認と検証の単位として大きすぎる |
| D2 | 起動の仕方 | **a**: 実行 ID を渡して呼べる関数と手動の実行手順だけ ／ **a+b**: 加えて、実行が失敗したとき自動で走らせ、診断結果を Slack の失敗通知の後に続けて投稿する（機能フラグで既定オフ） | **a+b**。「自律して」に応えるには自動の起動が要る。既存の失敗通知は文面も順序も変えず、その**後**に 2 通目として足すので、既存の挙動は変わらない。変更は `main.py` の失敗時の経路に限られ、`orchestrator.py` は無変更 |
| D3 | プロンプト記録を読むツール | 含める ／ 外す | **含める**。出力の検証失敗などは全文を見ないと原因が分からない。ただしタスクロールは S3 の**書き込み権限しか持たない**（`template.yaml:494-500`）ため、ECS 上ではこのツールは「読めない」を返し、残りの記録だけで診断する。手動実行（開発者の権限）では読める。権限の追加は §7 |

以降は**推奨案を前提**に書く。

**本番で有効にするには**: フラグは環境変数で、未設定なら無効。ECS で有効にするには `template.yaml` への環境変数の追加が要り、あわせて S3 の読み取り権限も足すのが自然である。どちらも本作業に含めない（§7）。本作業の範囲では、本番の挙動は変わらない。

## 3. ユーザーストーリー

- ユーザーとして、実行が失敗したとき「どの段階で、なぜ失敗し、次に何をすればよいか」を、ログを自分で追わずに知りたい。
- 開発者として、実行 ID を渡すだけで、エージェントが記録を自分で調べて診断を返してほしい。成功した実行の異常（レビューで不合格が続いた等）も調べたい。
- 開発者として、診断役が**何を見てそう判断したか**（どのツールを、どの順で呼んだか。どの記録を根拠にしたか）を後から確かめたい。
- 開発者として、記録が足りないときは、推測で埋めず「分からない」と返してほしい。
- 運用者として、記録の中身（Web から取った文章など）に指示文が混ざっていても、診断役にできることが増えないでほしい。
- 運用者として、診断役が失敗しても、既存の失敗通知と後始末は今までどおり行われてほしい。

## 4. 要件

### 4.1 記録を読むツール（読み取り専用・4 個）

| ツール | 返すもの |
|---|---|
| 実行の概要 | 状態、開始・完了時刻、トピック、カテゴリ、トークン・費用の合計 |
| 段階の一覧 | 各段階の ID・状態・開始・完了時刻 |
| イベントの一覧 | 時系列のイベント（種別・時刻・payload）。種別での絞り込みと、1 回あたりの件数の上限つき |
| プロンプト記録の取得 | 指定した役と番号の、プロンプトと出力（先頭と末尾を残した切り詰め、元の大きさつき） |

- R1: ツールが読めるのは、**コードが渡した実行 ID の記録だけ**。ツールの入力スキーマに、実行 ID・テーブル名・バケット名・キーを指定する項目を持たせない。実行 ID は呼び出し側が形式を検証してから固定する。
- R2: 入力はモデルが作った信頼できない値として検証する（型、必須項目、未定義の項目、取りうる値、長さ）。プロンプト記録の「役」は決まった値のみ、「番号」は英数字・ハイフン・下線のみとし、S3 のキーに区切り文字が入り込まないようにする。
- R3: ツールは読み取りだけを行う。DynamoDB・S3 への書き込み・更新・削除を行わない。
- R4: ツールが返す各記録に、コードが**根拠 ID** を振る。診断結果はこの ID で根拠を指す（R11）。
- R5: 読み取るサイズに上限を持つ。1 回の結果の大きさ、文字列項目 1 つの長さ、1 実行あたりの累計。超えるぶんは切り詰め、切り詰めたことを結果に示す。
- R6: ツールは例外を外に出さない。失敗は固定の分類で返す。

| 失敗分類 | 条件 |
|---|---|
| `invalid_input` | 入力の検証に通らない |
| `not_found` | 該当する記録がない |
| `unavailable` | 権限がない、または保存先が設定されていない（ECS 上のプロンプト記録など） |
| `call_limit` | ツール呼び出し総数の上限を超えた |
| `size_limit` | 累計の読み取りサイズの上限を超えた |
| `internal_error` | 上記以外の想定外の例外。例外メッセージは結果に入れず、ログに残す |

- R7: 秘密情報らしい値（トークン・キーの形をした文字列）は、ツールの結果の段階でマスクする。Slack のユーザー ID・チャンネル・スレッドの識別子は返さない（ユーザー ID が要るなら、既存の `topic_received` と同じく SHA-256 の先頭 16 桁にする。`src/trigger/app.py:705-712`）。

### 4.2 診断結果

- R8: 診断結果は固定の構造を持つ。

| 項目 | 形 |
|---|---|
| 失敗した段階 | 決まった値から 1 つ（計画 / 調査 / 生成 / レビュー / 格納 / 通知 / 該当なし / 不明）。値は design.md で既存の状態名に揃える |
| 原因の分類 | 決まった値から 1 つ（レート制限 / 外部サービスのエラー / 調査の失敗 / 出力の検証失敗 / レビュー不合格 / 認証・環境 / 記録の不足 / 不明） |
| 原因の性質 | 決まった値から 1 つ（コードの不具合 / 一時的な失敗 / 入力やプロンプトの問題 / 環境・設定の問題 / 不明） |
| 例外の型 | 識別子の形の文字列（英数字と下線のみ）。コードがイベントの記録から取り出す。モデルは、どのイベントのものかを根拠 ID で選ぶだけで、文字列は書かない |
| 関係するコードの場所 | ファイルのパス・関数名・行番号の組（0 件以上、上限つき）。コードがスタックトレースから決まった形で取り出して ID を振る。モデルはその ID を選ぶだけで、文字列は書かない |
| 根拠 | 根拠 ID の一覧と、それぞれの短い説明 |
| 推奨する対処 | 分類（時間を置いて再投入 / すぐ再投入 / 設定の見直し / コードの修正 / 対処不要 / 人による調査）と短い説明 |
| 確からしさ | 高 / 中 / 低 |
| 要約 | 長さの上限つきの短い文 |

- R9: 診断結果は、モデルが**提出用のツール**を呼んで出す（最終テキストから読み取らない）。提出はコードが検証し、形が不正なら `is_error` で返して出し直させる。受理した提出が正本となる。
- R10: **「分からない」は正当な結果**である。原因の分類「不明」「記録の不足」は、根拠なしでも受理する。
- R11: **根拠の照合**。根拠 ID は、その実行でツールが実際に返したものに限る。返していない ID は無効として取り除き、無効だった件数を結果に残す。「不明」「記録の不足」以外の分類で有効な根拠が 1 つも残らない場合は、原因の分類を「不明」、確からしさを「低」に落とす。
- R12: 自由記述（説明・要約）には長さの上限を設け、R7 と同じマスクを通す。
- R12a: **受け渡し用の診断結果**。診断結果から、次の項目だけを取り出したものを別に作る: 実行 ID、失敗した段階、原因の分類、原因の性質、確からしさ、例外の型、関係するコードの場所、推奨する対処の分類、有効な根拠の件数。**自由記述（説明・要約）と、記録の中身は一切含めない**。すべて決まった値か、形を検証した識別子である。第 2 段階の修正役が受け取るのはこれだけである。
- R12b: **原因の性質ごとの扱い**をコードが決める（モデルに決めさせない）。

| 原因の性質 | 扱い |
|---|---|
| コードの不具合 | 確からしさが「高」で、有効な根拠が 1 件以上あり、コードの場所が 1 件以上あるときだけ「修正役に渡せる」。それ以外は人による調査の提案 |
| 一時的な失敗 | 再投入の提案だけ |
| 入力やプロンプトの問題 | 提案だけ |
| 環境・設定の問題 | 提案だけ |
| 不明 | 何もしない |

「修正役に渡せる」かどうかは、受け渡し用の診断結果にコードが書き込む。第 1 段階では、この判定を出すところまでを行い、修正役の起動はしない。

### 4.3 実行診断役（SDK への渡し方と上限）

- R13: ツールは SDK の `@tool` と `create_sdk_mcp_server` で定義・登録する。ツールの中身は SDK に依存しない関数に分け、単体でテストできるようにする。ハンドラーから例外を漏らさない。
- R14: 診断役に渡すオプションは、組み込みツールをすべて外し（`tools=[]`）、許可は自分で定義した 5 個（読み取り 4 + 提出 1）だけ。書き込み・通信・シェルのツールを持たせない。モデル名は設定で変えられる。
- R15: 上限。ターン数（`max_turns`、案: 15）、全体の制限時間（案: 180 秒）、ツール呼び出し総数（案: 20）、累計の読み取りサイズ（案: 200KB）。すべて設定で変えられる。診断結果の提出は、ツール呼び出し総数と累計サイズの上限に数えない（上限に達した後でも「分からない」を提出できるようにするため）。
- R16: 診断役は例外を外に出さず、必ず結果オブジェクトで終わる。終了理由は `completed`（提出を受理）/ `incomplete`（上限に達して提出なし）/ `failed`（SDK の失敗）。`incomplete` と `failed` では、原因の分類「不明」の診断結果と、それまでの足取りを返す。
- R17: 上限への到達と SDK の失敗を、**既存の再試行・上位モデルへの切り替え（`_run_claude_with_retries`）に乗せない**。SDK の呼び出しは 1 回だけ。
- R18: 記録の中身（Web から取った内容、プロンプト、生成物、エラー文）は信頼できない入力として扱う。ツールの結果としてだけモデルに渡し、診断役への指示文には混ぜない。R1・R3・R14 により、指示文が混ざっていても、読める範囲もできることも増えない。R9・R11 により、診断結果の形と根拠はコードが検証する。

### 4.4 足取りの記録

- R19: 診断役が呼んだツールを、順番どおりに記録する（ツール名、検証後の引数、結果の分類、返した根拠 ID の件数、所要時間）。失敗した呼び出しも含む。この記録はツールのハンドラーの側で取る（SDK の途中のメッセージに頼らない）。
- R20: 足取りは結果オブジェクトに入れ、終了時にイベント 1 件（`diagnosis_completed`。当初は仮称で、この名前で確定）として既存の `EventEmitter` で残す。payload は終了理由、原因の分類、確からしさ、ツール名の並び、件数、所要時間、トークン数、受け渡し用の診断結果（R12a。本番の自動診断の結果を第 2 段階へ渡せるようにするため）。自由記述・記録の中身・Slack の識別子は入れない。あわせてログ 1 行を出す。
- **既存の役（調査・生成・レビュー）の途中経過は、今回は記録しない**。`_query_claude_sync`（`src/agent/orchestrator.py:562-571`）が `ResultMessage` 以外を捨てているため、どのツールをどの引数で呼んだかは残っていない。これを残すには 3 つの wrapper が共有する中核の呼び出し経路に手を入れることになり、過去の障害対応（最初の `ResultMessage` で返す挙動）とも重なるため、別の作業単位とする（§7）。その結果、診断役は既存の役の足取りに関する問い（どの URL を取りに行ったか等）には答えられず、**推測せず「記録の不足」と返す**。

### 4.5 起動

- R21: **関数**。実行 ID を渡して呼ぶと、診断結果と足取りを返す。成功した実行にも使える。実行 ID の形式が不正なら、記録にも SDK にも触れずに `failed` を返す。
- R22: **失敗時の自動起動**（機能フラグ、環境変数、既定オフ）。オンのとき、実行が失敗したら、**既存の失敗通知を今までどおり送った後に**診断役を 1 回走らせ、診断結果を同じ Slack スレッドに 2 通目として投稿する（投稿するのは終了理由が `completed` のときだけ。`incomplete`・`failed` では投稿せず、イベントとログだけ残す）。オフのとき、診断役のコードは 1 行も実行されない。
- R23: 自動起動は次の場合に行わない。Claude の呼び出しがレート制限・使用上限で失敗した場合（診断役も同じ理由で失敗するため）、認証情報の準備より前に失敗した場合、フィードバック処理の失敗、実行 ID が分からない場合。
- R24: 診断役の失敗・時間切れ・Slack 投稿の失敗は、元の例外・既存の失敗通知・終了時の認証情報の書き戻しに影響しない。
- R25: Slack への投稿文は、診断結果の固定項目からコードが組み立てる。メンション記法を無効化し、R7 のマスクを通す。

### 4.6 非機能

- R26: ネットワークも認証情報も使わずに §5 の必須条件がすべて通る。DynamoDB・S3・SDK・時計は差し替える。
- R27: 実際に動かす確認は、pytest の既定実行に含めない手動手順として文書にする。
- R28: 依存パッケージを追加しない。`ruff`（`S` ルールを含む既存設定）に通る。

## 5. 受け入れ条件

特記のない限り、DynamoDB・S3・SDK を差し替えた自動テスト（`tests/unit`）で確認する。

**自動テストが保証する範囲**: ツール・上限・検証・照合・起動の経路が仕様どおり動くこと。**診断が当たるかどうか**（モデルの判断の質）は自動テストでは確かめられず、任意条件 O1 の手動確認で見る。

### 必須

**記録を読むツール**

1. **概要**: 偽の実行レコード → 状態・時刻・トピック・カテゴリ・合計が返る。Slack のユーザー ID・チャンネル・スレッドの値は結果に含まれない。
2. **段階の一覧**: 偽の段階レコード 3 件 → 3 件が ID・状態・時刻つきで返り、それぞれに根拠 ID が付く。
3. **イベントの一覧**: 時系列順に返る。種別で絞り込める。1 回あたりの件数の上限を超えるぶんは返らず、続きがあることが結果に示される。長い文字列項目（`stack_trace` など）は上限で切り詰められ、切り詰めの印が付く。
4. **プロンプト記録**: 役と番号を指定 → プロンプトと出力が先頭・末尾を残して上限内に切り詰められ、元の大きさが示される。
5. **範囲の縛り**: 4 個のツールの入力スキーマに、実行 ID・テーブル・バケット・キーの項目がない。入力に `execution_id` を足して呼ぶ → `invalid_input`。1 回の診断で偽クライアントが受けた呼び出しは、すべてコードが渡した実行 ID と決まったテーブル・キーの接頭辞だけを使っている。
6. **番号と役の検証**: 番号に `../` や `/` を含む値、役に決まった値以外 → `invalid_input`、S3 は呼ばれない。
7. **記録がない・読めない**: 実行レコードがない → `not_found`。S3 が権限エラー、または保存先が未設定 → `unavailable`。該当のキーがない → `not_found`。いずれも例外は出ない。
8. **想定外の例外**: 偽クライアントが想定外の例外を出す → `internal_error`。例外メッセージは結果に含まれず、ログに残る。
9. **上限**: ツール呼び出し総数の上限を超えた呼び出し → `call_limit`、記録は読まれない。累計の読み取りサイズの上限を超えた呼び出し → `size_limit`。
10. **マスク**: Slack・GitHub のトークン、`Bearer` つきの値、AWS のアクセスキーの形をした文字列を含む記録 → ツールの結果ではマスクされている。
11. **書き込みなし**: 本作業の全テストを通じて、偽の DynamoDB・S3 クライアントが受ける操作は読み取りだけである（イベントの emit を除く）。

**診断結果**

12. **提出の検証**: 形の正しい提出 → 受理。決まった値以外の分類・必須項目の欠落・長さ超過 → `is_error` で受理されず、出し直しができる。受理した自由記述は R7 のマスクを通っている。
13. **根拠の照合**: ツールが返した根拠 ID → 有効として残る。返していない ID → 取り除かれ、無効の件数が結果に残る。
14. **根拠ゼロ**: 「レート制限」と提出したが有効な根拠が 0 件 → 原因の分類は「不明」、確からしさは「低」になる。
15. **「分からない」**: 「不明」または「記録の不足」を根拠なしで提出 → 正常な結果として受理（終了理由 `completed`）。

**実行診断役**

16. **オプション**: SDK に渡すオプションで、`tools` が空リスト、`allowed_tools` が自分で定義した 5 個だけ、`mcp_servers` にサーバーが登録され、`max_turns` と `model` が設定値どおりである。
17. **終わり方**: (a) SDK が `error_max_turns` を返す、(b) 全体の制限時間を超える、(c) SDK が例外を出す、(d) 実行 ID の形式が不正 → いずれも例外は出ない。(a)(b) は `incomplete`、(c)(d) は `failed`。診断結果は「不明」で、それまでの足取りが残る。SDK の呼び出しは (a)〜(c) で 1 回だけ、(d) は 0 回。
18. **足取り**: 偽の SDK が「概要 → イベント → 不正な入力でプロンプト記録 → 提出」の順でツールを呼ぶ → 結果の足取りが同じ順で 4 件あり、それぞれにツール名・結果の分類・根拠 ID の件数・所要時間がある。失敗した 3 件目も含まれる。
19. **筋書き**: 次の 5 つを偽の記録で用意する。それぞれ、決め手となる記録がツールの結果に根拠 ID つきで現れ、その ID を引いた提出が期待どおりの診断結果として受理される。
    - 調査が全滅（全段階が失敗、`subagent_failed`）
    - 出力の検証に失敗（`NonDictGeneratorResponse` の `subagent_failed`）
    - レート制限（`rate_limit_hit`）
    - レビューで不合格が続いた（`review_completed` が上限回数まで不合格。実行自体は成功）
    - 記録が欠けている（イベントが空、プロンプト記録が `unavailable`）→ 「記録の不足」

**起動**

20. **フラグ既定オフ**: 環境変数が未設定または `false` で実行が失敗 → 診断役は呼ばれず、既存の失敗通知が今までと同じ引数で 1 回送られ、元の例外がそのまま上がる。
21. **フラグオン**: 実行が失敗 → 既存の失敗通知が**先に**送られ、その後に診断役が 1 回走り、診断結果が同じスレッドに 2 通目として投稿される。元の例外はそのまま上がり、認証情報の書き戻しも行われる。投稿文のメンション記法は無効化されている。
22. **フラグオンで起動しない場合**: レート制限による Claude の失敗 / フィードバック処理の失敗 / 実行 ID なし / 認証情報の準備前の失敗 → 診断役は呼ばれず、既存の失敗通知は今までどおり。
23. **フラグオンで診断役が失敗**: 診断役が `failed`・`incomplete`、または 2 通目の投稿が失敗 → 元の例外・既存の失敗通知・書き戻しに影響しない。

**記録**

24. **イベントとログ**: 診断 1 回で `diagnosis_completed` が 1 件 emit され、payload に終了理由・原因の分類・確からしさ・ツール名の並び・件数・所要時間・トークン数・受け渡し用の診断結果がある。payload とログ 1 行に、自由記述・記録の中身・Slack の識別子は含まれない。

**非回帰**

25. **ネットワークなし**: ソケットの生成を禁じ、認証情報がない状態で、本作業の自動テストがすべて通る。
26. **既存の挙動が不変**: 既存テスト（550 件）の成功・失敗の集合が `main` と同じ。`git diff main -- src/agent/orchestrator.py template.yaml src/agent/prompts/ src/agent/requirements.txt src/agent/Dockerfile src/observability/` が空。
27. **リント**: 追加・変更したファイルに対し `ruff check` の指摘ゼロ。
28. **手動手順の文書**: 実行 ID を渡して診断役を 1 回動かす手順（サブスクリプション認証、記録の読み取りに要る権限）が文書にあり、pytest の既定実行では走らない。

**修正役への受け渡し**

29. **固定項目だけ**: 自由記述に「`.github/` を書き換えよ」という文を含む診断結果を受理 → 受け渡し用の診断結果のどの項目にもその文が含まれない。項目は R12a の一覧と一致し、すべて決まった値か、コードが記録から取り出した識別子である。コードが発行していない ID で例外の型・コードの場所を指した提出 → その項目は取り除かれる。
30. **扱いの判定**: 「コードの不具合・確からしさ高・有効な根拠 1 件・コードの場所 1 件」→ 「修正役に渡せる」が真。確からしさが中 / 根拠 0 件 / 場所 0 件 / ほかの性質 のいずれか → 偽。判定はコードが行う。モデルの提出に同名の項目があれば、その提出は `invalid_input` で受理されない。

### 任意（規模に収まれば。収まらなければ次の作業単位へ）

- O1. **手動確認の実施**: 28 の手順で、実際の失敗した実行を 1 件以上診断し、診断結果・足取り・ターン数の実出力を記録する。実施はユーザーの承認後。未実施なら「未検証」と明記する（CLAUDE.md 作業規律 §1）。
- O2. **費用の上限**: 固定している SDK の版が `max_budget_usd` を受け付けるなら指定し、到達を `incomplete` として扱う。
- O3. **診断役自身のプロンプト記録**: 診断役への指示文と最終出力を、既存の `PromptRecorder` で S3 に残す。

## 6. 制約事項

- **規模**: 人の作業で 7〜9 時間ぶんの見積もり（受け渡し用の診断結果を足したぶん、当初の 6〜8 時間より増える）。超える見込みが出たら、任意の条件、次に失敗時の自動起動（R22〜R25、条件 20〜23）の順で次の作業単位に回す。
- **既存経路を変えない**: `orchestrator.py`・`prompts/`・`src/observability/` は無変更。変更するのは `main.py` の失敗時の経路（フラグ判定と診断役の呼び出し）だけで、既存の失敗通知の文面・順序・条件は変えない。
- **認証は変更しない**: 既存のサブスクリプション認証をそのまま使う。
- **`template.yaml` を変更しない・デプロイしない**。
- **権限の現状**（`template.yaml:445-500`）: タスクロールは、実行・段階・イベントの各テーブルへの `GetItem`・`Query` を持つ。S3 のプロンプト記録は `PutObject` のみで、**読み取りはできない**。CloudWatch Logs は書き込みのみ。
- **費用の集計**: 診断役のトークンは、実行の合計（`total_tokens_used` など）には足さない。失敗時の自動起動は、合計を書き込んだ後に走るためである。診断役のぶんは `diagnosis_completed` に残す。
- **タスクの実行時間**: 自動起動がオンのとき、失敗した実行の ECS タスクは、診断役の制限時間ぶん長く動きうる。
- **SDK の仕様の確認状況**: `@tool`・`create_sdk_mcp_server`・ツール名の形（`mcp__<サーバー>__<ツール>`）・`tools=[]`・`allowed_tools` は許可であって制限ではないこと・`max_turns`・`ResultMessage.subtype`・ハンドラーの例外は生の文言でモデルに渡ること・Python の `@tool` はハンドラーの戻り値のうち `content` と `is_error` だけを渡すことは、公式文書（2026-10-04 時点の最新版）で確認済み。固定している版 `claude-agent-sdk==0.2.110` に、`tool`・`create_sdk_mcp_server` と、`ClaudeAgentOptions` の `tools`・`allowed_tools`・`disallowed_tools`・`mcp_servers`・`max_turns`・`max_budget_usd`・`setting_sources`・`cwd` があることは、導入済みのパッケージで確認済み（2026-10-04、司令塔）。**未確認のまま**: `tools=[]` を渡したときの実際の挙動、`error_max_turns` のとき `is_error` が真か、`max_budget_usd` の実際の効き方（実際に LLM を呼ばないと分からない）。設計は、どちらでも壊れない作りにする。
- **リントの読み方**: AC-27 の「指摘ゼロ」は、追加・変更したファイルについてである。リポジトリ全体には、変更前から既存の指摘が 32 件ある（2026-10-04、`ruff check src tests`）。
- **テストの基準**: 変更前は 550 passed（`TMPDIR=/tmp` と AWS のダミーの環境変数を付けて実行。`TMPDIR=/tmp` を付けないと macOS では既存の 2 件が落ちる）。
- 実装コミット後は CLAUDE.md 作業規律 §4（Codex レビューゲート）に従う。
- **承認の記録（2026-10-04）**: 司令塔が、要求定義 2 件（本ファイルと `.steering/20261004-execution-fixer/requirements.md`）の要点、判断点（推奨つき）、規模、「設計書とタスク一覧をまとめて作ってよいか」「第 2 段階を続けて進めるか」を示して承認を求め、ユーザーは次のとおり答えた（司令塔からの伝達による）。
  > 「『直す』ところまで自律して進めていただいて良いです」
  - 司令塔の受け取り: (1) 要求定義 2 件の承認。判断点は推奨どおり。(2) 設計書・タスク一覧・実装の各段階で個別に承認を求めず、修正役の完成まで進めてよい。これは CLAUDE.md 作業規律 §2 の「前段の承認なしに次のファイルを作成しない」に対する、この 2 つの作業単位に限った許可である。

## 8. 文書への影響

- **ADR-0001 との関係**: 矛盾しない。Agent SDK を使い続け、その上にカスタムツールと小さな役割を足すだけである。同期ファサードの呼び出し経路にも触れない。
- **新しい ADR**: 今回は不要と考える。フラグを切れば元に戻せ、消しても既存の流れに影響しないため「覆すのが困難」に当たらない。「記録の中身は信頼できない入力として扱う」「根拠はコードが照合する」という線引きは `design.md` に理由つきで残す。**「記録を読む役と、コードを書き換える役を分け、間は固定項目だけでつなぐ」という決定は ADR の候補**である（第 2 段階の requirements.md §8 を参照）。
- **`docs/product-requirements.md`**: 「自律」は現在、ワークフローの設計と成果物の選択についてのみ書かれている（FR-3 など）。実行の診断は新しい機能なので、承認後に機能一覧へ追記する。
- **`docs/glossary.md`**: 「実行診断役」「カスタムツール」「診断結果」「足取り」の登録が要る（名称は仮称）。既存の「サブエージェント」（リサーチャー・ジェネレーター・レビュアーの 3 種）に診断役を加えるかどうかも、ここで決める。
  - **（2026-10-05 追記）名称は確定し、登録済み**。実行診断役は、オーケストレーターから起動されないので、「サブエージェント」には加えていない（用語集 §7 に使い分けを書いた）。
- **`docs/functional-design.md`**: エラー処理の表（失敗時の通知）に、診断の 2 通目を追記する（実装時）。
