## 1. 背景・問題

第 1 段階の実行診断役は、実行記録を自分で調べて「どの段階で、なぜ失敗したか」を返す。原因がコードの不具合だと分かっても、そこから先（再現するテストを書く、直す、確かめる）は人の作業のままである。

ユーザーの要望は「エージェントが自律してデバッグできるようにする。『直す』までやる」である。

一方、コードを書き換える役には、次の危険がある。

- 実行記録には Web から取った文章・プロンプト・生成物が入っており、指示文が仕込まれうる。それがコードを書き換えられる役に届くと、意図しない変更をさせられる。
- モデルの「直しました」「テストは通りました」という申告は、そのままでは信用できない。
- 誤った修正が main や本番に届くと、影響が大きい。

## 2. 変更・追加する機能

**修正役**を追加する。第 1 段階が出した**受け渡し用の診断結果**を受け取り、リポジトリの複製の中で、失敗を再現するテストと修正を作り、**コードによる合否の検査**に通ったものだけを作業用ブランチにコミットして、プルリクエストの本文の下書きを添える。

### 「直す」の範囲

| | 内容 |
|---|---|
| **含む** | コードの不具合に対する修正と再現テストの作成 ／ コードによる合否の検査 ／ 作業用ブランチへのコミット（手元のみ）／ プルリクエスト本文の下書き |
| **含まない** | プッシュ ／ プルリクエストの作成 ／ main への取り込み ／ デプロイ ／ 本番の実行の自動やり直し ／ 設定・インフラ・プロンプトの修正 |

main への取り込みは必ず人が行う。

### 二段構え（権限の分離）

| | 実行診断役（第 1 段階） | 修正役（本作業） |
|---|---|---|
| 読むもの | 実行記録（信頼できない） | 受け渡し用の診断結果（固定項目）と、リポジトリの複製 |
| できること | 読み取りだけ | 複製の中でのファイルの読み書きと、決まったテストの実行 |
| 動く場所 | 本番のコンテナ、または手元 | **手元の、リポジトリの複製がある環境だけ**。本番のコンテナでは動かさない |
| 本番の認証情報 | 記録の読み取りに使う | **置かない** |

修正役が受け取るのは、次の固定項目だけである（第 1 段階 R12a）: 実行 ID、失敗した段階、原因の分類、原因の性質、確からしさ、例外の型、関係するコードの場所（パス・関数名・行番号）、推奨する対処の分類、有効な根拠の件数、「修正役に渡せる」の判定。**診断役の自由記述と、実行記録の中身（エラーメッセージの文面を含む）は渡さない**。

**コードの場所は「手がかり」であり、正解ではない**。第 1 段階は、場所を実際のコードと突き合わせて、実在する関数の中の行だけを通す。しかし、**どの実在の関数を指すかは、記録の側から選べる**ことが分かっている（例外メッセージに、本物と同じ形の行を仕込まれた場合）。そのため修正役は、場所を調べ始める入口として扱い、ほかの場所も読んで自分で不具合を確かめる。場所が指す関数に不具合が見つからなければ、変更せずに終わる。誤った場所を指されても害が出ないことは、合否の検査（修正前に落ち、修正後に通る再現テストが要る）と、人による確認が担保する。

この分離の代償として、修正役は「何が起きたか」の説明文を持たない。例外の型とコードの場所から、コードを読んで自分で不具合を突き止める必要があり、直せない場合が増える。直せないときは「直せなかった」と返すのを正当な結果とする。

### 確認が必要な決定（推奨つき）

| # | 決める点 | 選択肢 | 推奨と理由 |
|---|---|---|---|
| D1 | プッシュとプルリクエストの作成 | **a**: 実装しない。人が `git push` と PR 作成を手で行う（手順を文書にする）／ **b**: 機能フラグと人の明示の操作で行う機能を作る | **a**。修正役に GitHub への書き込みの認証情報を一切持たせずに済み、誤った修正が手元から出ない。手間は 2 コマンドぶん。実際に何度か使ってから b を検討する |
| D2 | 作業規律（CLAUDE.md）との関係 | **a**: 規律は変えない。修正役の成果物は「提案」であり、取り込む前に人が規律どおり steering を起こして承認し、プッシュ後に Codex レビューを通す ／ **b**: 「診断に基づく小さな不具合修正は、PR の下書きを steering の代わりにできる」という例外を CLAUDE.md に足す | **a**。規律の変更はユーザーの承認事項であり、修正役の当たり具合が分かる前に緩めるべきではない。a では、修正役が再現テストと修正案と下書きを用意し、人が文書と承認を担う。b を選ぶ場合は、CLAUDE.md の改訂を別途ユーザーが承認する |
| D3 | 起動の仕方 | **a**: 人が受け渡し用の診断結果を指定して、手で起動する ／ **b**: 診断役が「修正役に渡せる」と判定したら自動で起動する | **a**。修正役は手元でしか動かず、本番のコンテナから起動する経路がそもそもない。自動の連結は、CI で動かす段（§7）で検討する |
| D4 | 既存のテストの変更 | **認めない**（新しいテストファイルの追加だけ）／ 認める | **認めない**。既存のテストを書き換えて「通った」ことにする抜け道を塞ぐ。既存のテストの変更が要る修正は、人に回す |

以降は**推奨案を前提**に書く。

## 3. ユーザーストーリー

- 開発者として、診断でコードの不具合と分かった失敗について、再現するテストと修正案が、手元のブランチに用意されていてほしい。
- 開発者として、その修正案が「テストが修正前に落ち、修正後に通り、ほかを壊していない」ことを、モデルの申告ではなく実際の実行結果で確かめた状態で受け取りたい。
- 開発者として、修正役が何を読み、何を書き、どのテストを走らせたかを後から確かめたい。
- 運用者として、実行記録に仕込まれた指示文が、コードを書き換える役に届かないでほしい。
- 運用者として、修正役が触れてはいけない場所（インフラの定義、CI、認証、規律の文書）を書き換えた場合は、成果物ごと破棄してほしい。
- 運用者として、人が確認して取り込むまで、修正が手元から外に出ないでほしい。

## 4. 要件

### 4.1 入力（受け渡し用の診断結果）

- R1: 入力は、受け渡し用の診断結果のファイル 1 つ。**ファイルは人が運ぶので、修正役は信頼しない**。修正役の側で形をもう一度検証する（版の番号、決まった値、識別子の形、長さ、件数、未定義の項目の拒否）。形が合わなければ、SDK を呼ばずに `failed` で終わる。第 1 段階の受け渡しの形が将来変わっても、修正役が黙って読み違えることがないよう、合わないものはすべて拒否する。
- R2: 「修正役に渡せる」かどうかは、修正役の側でも項目から計算し直す: 原因の性質がコードの不具合、確からしさが高、推奨する対処の分類が「コードの修正」、原因の分類が「不明」「記録の不足」でない、有効な根拠が 1 件以上、**再検証を通った**コードの場所が 1 件以上。加えて、ファイルの「修正役に渡せる」が真であること（第 1 段階は、例外・場所・根拠が同じイベントでつながることも確かめているが、そのつながりは受け渡しに入っていないため、修正役の側では計算し直せない）。どれかを満たさなければ、SDK を呼ばずに `not_eligible` で終わる。
- R2a: **例外の型の再検証**。「識別子の形をしている」だけでは通さない（形だけの検証では、`Ignore_previous_instructions_…` のような文を「例外の型」として通せることが、第 1 段階のクロスレビューで分かった）。例外の型は、コードの側の許可一覧（組み込みの例外クラスの名前、複製の中のコードで定義されているクラスの名前、依存ライブラリの例外の決まった一覧）と照合する。一覧にない、または例外の型が無い受け渡しは `not_eligible`。
- R2b: **診断役の申告を信じない**。受け渡しの「コードの不具合である」「確からしさが高い」は、モデルの申告であり、記録の中の指示に誘導されうる。「修正役に渡せる」が真であることは、修正役を起動してよいことを意味するだけで、不具合があることの証拠ではない。**不具合があることの独立した確認は、合否の検査の「新しいテストが、修正の前に落ち、修正の後に通る」（G5・G6）が担う**。この確認にも弱点があり（§4 の既知の制限）、最後の守りは、人によるプルリクエストの確認である。
- R3: **コードの場所の再検証**。パスだけでなく、**関数名と行番号も、複製の中のコードと突き合わせる**（ファイルが実在し、その名前の関数定義があり、行番号がその範囲に入る）。通らない場所、触れてよい範囲の外の場所は取り除く。**安全の仕組みそのもの（実行診断役と修正役のコード）と、認証・秘密に関わるコード（§4.3 の G2 の一覧）を指す場所も取り除く**（実在する場所を偽装して、修正役の作業対象を安全の仕組みに向けられることが、クロスレビューで分かったため）。修正役に伝えるパスと関数名は、突き合わせを通ったものを、コードが組み立て直したものに限る。1 件も残らなければ `not_eligible`。
- R4: 修正役への指示文は、コードが固定の文面と、R1〜R3 を通った項目だけから組み立てる。自由記述は入らない。指示文は、場所を「ここを直せ」ではなく「**失敗が観測された場所**」として渡し、それが手がかりにすぎないこと、ほかの場所も読んでよいこと、直せないと判断したら変更せずに終わってよいことを伝える。

### 4.2 修正役（SDK への渡し方と縛り）

- R5: 既存の Claude Agent SDK を使う。認証は、手元の開発者自身のサブスクリプション認証。
- R6: 作業は、リポジトリの**作業用の複製**（基準のコミットから作る）の中だけで行う。複製には **`.git` を置かない**（モデルにも、修正役が走らせるテストにも、リポジトリの履歴・設定・フックを触らせないため）。
- R6a: **ファイルの読み書きも、自分で定義したカスタムツールで行う**（SDK の組み込みツールは使わない）。ツールは、呼び出しのたびにパスを複製の根からの相対パスとして解決し、複製の外（絶対パス、`..`、複製の外を指すシンボリックリンク）への読み書きを、その場で拒否する。書き込みは `src/` と `tests/` の下だけに限り、禁止の場所（§4.3 の G2）と既存のテストファイルへの書き込みも、その場で拒否する。
- R7: **シェルを持たせない。通信のツールを持たせない**。テストの実行は、自分で定義したカスタムツール（テスト実行ツール）だけで行う。このツールは、コードが決めたコマンドで pytest を走らせ、モデルが指定できるのは複製内のテストのパスだけである。
- R7a: 組み込みツールをすべて外し、許可は自分で定義したツールだけにする。起動時のツール一覧、または途中の呼び出しに、自分で定義したもの以外が見えたら中断する（第 1 段階と同じ備え）。
- R7b: ツールの入力は、モデルが作った信頼できない値として、自分のコードで検証する。検証に落ちた呼び出しも足取りと回数に残す（SDK の側の検証には頼らない）。
- R8: テストの実行は、環境変数を**決まった一覧だけ**に絞り（親の環境変数を引き継がない。AWS の値は、既存のテストが要るダミーの値だけを入れる）、ホームディレクトリを空の一時ディレクトリに向け、制限時間をつけて行う。
- R9: 上限。ターン数（案: 30）、全体の制限時間（案: 20 分）、テスト実行の回数（案: 10）と 1 回の制限時間（案: 5 分）。すべて設定で変えられる。
- R10: 上限への到達と SDK の失敗を、既存の再試行・上位モデルへの切り替えに乗せない。
- R11: 修正役は例外を外に出さず、必ず結果オブジェクトで終わる。

| 終了理由 | 条件 |
|---|---|
| `proposed` | 合否の検査にすべて通り、作業用ブランチにコミットした |
| `rejected` | 合否の検査のどれかに通らなかった。成果物は破棄 |
| `declined` | 修正役が「直せない」と返した（正当な結果） |
| `incomplete` | 上限に達した。成果物は破棄 |
| `not_eligible` | 入力が条件を満たさない。SDK を呼んでいない |
| `failed` | SDK の失敗、複製の準備の失敗など |

### 4.3 合否の検査（コードが行う）

モデルの申告を信じず、修正役が終わった後に、コードが複製の差分と実際のテスト結果で確かめる。**1 つでも通らなければ、コミットせず、複製ごと破棄する**。

| # | 検査 | 通る条件 |
|---|---|---|
| G1 | 範囲 | 変更されたパスが、すべて `src/` または `tests/` の下にある |
| G2 | 禁止の場所 | `template.yaml`、`.github/`、`.steering/`、`CLAUDE.md`、`docs/`、`Dockerfile`、依存の定義（`requirements*.txt`、`pyproject.toml`）、`.gitleaks.toml`、認証に関わるコード、**修正役と実行診断役のコードそのもの**（安全の仕組みを自分で緩められないようにする）への変更がない。一覧は design.md |
| G3 | 既存のテスト | `tests/` の下の既存のファイル（`conftest.py` を含む）に変更・削除がない。`tests/` の下に足せるのは、新しいテストファイル（`test_*.py`）と、空の `__init__.py` だけである（テストの集め方や結果を変えるファイルを足せないようにする） |
| G4 | 再現テストがある | 新しいテストファイルが 1 件以上ある |
| G5 | 修正前に落ちる | 基準のコミットに新しいテストファイルだけを足した状態で、新しいテストが失敗する |
| G6 | 修正後に通る | 修正を足した状態で、新しいテストがすべて通る |
| G7 | ほかを壊さない | 既存のテストだけを走らせた結果（テストごとの成否）が、基準のコミットと、修正を足した状態とで同じである |
| G8 | リント | `ruff check` の指摘の数が、基準のコミットより増えていない |
| G9 | 大きさ | 変更したファイルの数と行数が上限以内（案: 5 ファイル、200 行） |
| G10 | 差分の中身 | シンボリックリンク・バイナリ・実行権限の変更がない。秘密情報らしい文字列がない |

G5〜G8 は、修正役が作業した複製ではなく、**コードが組み立て直したきれいな複製**（基準のコミット＋検査を通ったファイルだけ）で走らせる。

- R12: 検査の結果（どれに通り、どれに通らなかったか。テストの件数）は、結果オブジェクトに残す。

### 4.4 成果物

- R13: 検査にすべて通ったとき、**コードが**作業用ブランチにコミットする（モデルに git を触らせない）。ブランチ名とコミットメッセージは、コードが実行 ID と固定項目から決める。コミットに入るのは、検査を通ったファイルの中身だけである。元のリポジトリの作業ツリー・現在のブランチ・インデックスは変えず、フックも走らせない。同じ名前のブランチが既にあれば、修正役を起動する前に `failed` で終わる。
- R14: **プッシュしない。リモートに触れる操作を一切行わない**。
- R15: プルリクエストの本文の下書きを、複製の外のファイルとして出す。中身は、診断（固定項目）、変更点（コードが出した差分の要約）、検査の結果（コードが実行した結果）、モデルによる変更の説明（長さの上限つき、「モデルの説明・未検証」と明示）、症状パッチか構造修正かの申告、確かめていないこと（実機での確認は未実施、など固定の一覧）、足取り。
- R16: 下書きの冒頭に、取り込む前に人が行うこと（D2 の a に沿って: 内容の確認、規律どおりの steering と承認、プッシュ後の Codex レビュー）を固定の文面で入れる。あわせて、**「自動の検査は、再現テストが実際の失敗と同じ原因を突いていることまでは確かめていない。最後の確認は、このプルリクエストを読む人が行う」**という趣旨を、固定の文面で入れる。

### 4.5 足取りの記録

- R17: 修正役が呼んだツールを、順番どおりに記録する（ツール名、対象のパス、結果の分類、所要時間。テスト実行は、走らせたパスと成功・失敗の件数）。
- R18: 足取りと検査の結果は、結果オブジェクトと下書きに入れ、手元のファイルとして残す。本番の記録（events テーブル、S3）には書かない（修正役は本番の認証情報を持たないため）。

### 4.6 非機能

- R19: 修正役のコードは、本番のコンテナのイメージに含めない（`src/agent/` と `src/observability/` の外に置く）。第 1 段階のコード（決まった値、場所の突き合わせ、マスク）は、変更せずに再利用してよい。
- R20: 実際の LLM を呼ばずに、§5 の必須条件がすべて通る。SDK は差し替える。合否の検査は、一時ディレクトリに作った小さなリポジトリで確かめる。
- R21: 依存パッケージを追加しない。`ruff` に通る。

### 既知の制限

- **テストとして書かれたコードは、実行される**。修正役が書いたテストは pytest で走るため、その中身は手元の環境で動く。R8（環境変数とホームディレクトリの絞り込み）は緩和であって隔離ではない。本番の認証情報がない環境（コンテナなど）で動かすことを、手順で求める。
- **行番号がずれうる**。実行記録の行番号は、失敗した時点で本番に載っていた版のものであり、手元の複製の版と一致するとは限らない。関数名を併せて使う。
- **直せる範囲が狭い**。エラーメッセージの文面を渡さないため、例外の型と場所だけでは不具合を特定できない場合がある。安全の仕組みと、認証・秘密に関わるファイルは、ファイルごと対象外である。
- **独立した確認（G5・G6）の弱点**。修正役が、実際の失敗と無関係な「落ちるテスト」と、それを通すだけの変更を作れば、検査は通る。検査が確かめるのは「このテストが、この変更で、落ちる状態から通る状態になった」ことだけで、「実際に起きた失敗の原因を直した」ことではない。最後の守りは、人によるプルリクエストの確認である。
- **記録そのものを書き換えられる相手には効かない**。第 1 段階は、スタックトレースの最初のブロックからだけ場所を取るようにしたが、記録を直接書き換えられる相手は、1 行目から偽のトレースを書ける。また、記録の中の指示にモデルが誘導されれば、通常の失敗のほとんどで「修正役に渡せる」は真になりうる。根本策は §7（記録する側が、構造化した場所を残す）。

## 5. 受け入れ条件

特記のない限り、SDK を差し替え、一時ディレクトリの小さなリポジトリを使った自動テストで確認する。

**自動テストが保証する範囲**: 入力の検証、縛り、合否の検査、成果物の出し方が仕様どおり動くこと。**修正役が実際に直せるかどうか**は自動テストでは確かめられず、任意条件 O1 の手動確認で見る。

### 必須

**入力**

1. **形の検証**: 未定義の項目（自由記述など）を含むファイル / 決まった値以外 / 識別子の形でない値 → `failed`、SDK は呼ばれない。
2. **条件の再計算**: 確からしさが中 / 原因の性質が一時的な失敗 / 推奨する対処が「コードの修正」以外 / 原因の分類が「不明」 / 根拠 0 件 / コードの場所 0 件 → `not_eligible`、SDK は呼ばれない。ファイルの「修正役に渡せる」が真でも結果は変わらない。逆に、項目はすべて条件を満たすが、ファイルの「修正役に渡せる」が偽 → `not_eligible`。
3. **場所の再検証**: `/app/orchestrator.py` と、複製に実在する関数名・その範囲内の行番号 → 複製内の `src/agent/orchestrator.py` に対応づく。複製にないパス / `../` を含むパス / 実在しない関数名 / 関数の範囲の外の行番号 / 200 字を超える「関数名」 / 禁止の場所のファイル → 取り除かれ、1 件も残らなければ `not_eligible`。
4. **生の文面が渡らない**: 修正役への指示文は、固定の文面と固定項目だけからなる。入力ファイルに余分な自由記述の項目を足しても（1 で拒否されるが、検証を外した場合でも）、指示文を組み立てる関数はその項目を使わない。指示文に入るパスと関数名は、3 の再検証を通ったものだけである。指示文に、場所が手がかりであること・ほかの場所も読んでよいこと・変更せずに終わってよいことが書かれている。

**縛り**

5. **オプション**: SDK に渡すオプションで、組み込みツールがすべて外され（`tools` が空）、許可は自分で定義したツールだけで、作業ディレクトリが複製で、`max_turns` と `model` が設定値どおりである。起動時のツール一覧、または途中の呼び出しに、自分で定義したもの以外が現れる → 中断して `failed`。コミットはない。
6. **複製の外**: 読み取り・書き込み・一覧・検索の各ツールに、複製の外のパス（絶対パス、`../`、複製の外を指すシンボリックリンク）を渡す → 呼び出しの時点で拒否され、複製の外のファイルは読まれも書かれもしない。書き込みのツールに、`src/`・`tests/` の外、禁止の場所、既存のテストファイルを渡す → 同じく拒否される。複製に `.git` がない。
7. **テスト実行ツール**: 複製内のテストのパスを指定 → コードが決めたコマンドで走り、成功・失敗の件数が返る。パスに複製の外・オプションの文字列（`-` で始まる値）・区切り文字を混ぜる → `invalid_input`、何も実行されない。回数の上限を超える → `call_limit`。制限時間を超える → `timeout`。
8. **テスト実行の環境**: 親の環境変数に、目印の値を持つ `AWS_SECRET_ACCESS_KEY`・`AWS_SESSION_TOKEN`・`GITHUB_TOKEN`・`ANTHROPIC_API_KEY` を置いてテストを走らせる → テストの中から、その目印の値はどの環境変数にも見えない。見える環境変数は、決まった一覧だけである。ホームディレクトリは空の一時ディレクトリである。
9. **終わり方**: SDK が `error_max_turns` を返す / 全体の制限時間を超える → `incomplete`。SDK が例外を出す → `failed`。いずれも例外は出ず、コミットはなく、SDK の呼び出しは 1 回だけ。
10. **「直せない」**: 修正役が変更なしで終わる → `declined`。コミットはない。

**合否の検査**（それぞれ、通らない差分を偽の修正役に作らせる）

11. **G1 範囲**: `README.md` を変更 → `rejected`（G1）。
12. **G2 禁止の場所**: `template.yaml` / `.github/workflows/x.yml` / `CLAUDE.md` / `.steering/x/requirements.md` / `src/agent/requirements.txt` / 修正役のコード / 実行診断役のコード を変更 → それぞれ `rejected`（G2）。正しい修正と一緒に混ざっていても、全体が破棄される。
13. **G3 既存のテスト**: 既存のテストファイルを変更、または削除 / 既存の `conftest.py` を変更 / 新しい `conftest.py` を追加 / 中身のある `__init__.py` を `tests/` に追加 → それぞれ `rejected`（G3）。
14. **G4・G5 再現テスト**: 新しいテストがない → `rejected`（G4）。新しいテストが修正前でも通る → `rejected`（G5）。
15. **G6 修正後に通る**: 新しいテストが修正後も落ちる → `rejected`（G6）。モデルの最終テキストが「すべて通った」と述べていても結果は変わらない。
16. **G7 ほかを壊さない**: 修正で既存のテストが 1 件落ちるようになる → `rejected`（G7）。基準の時点で落ちていたテストは、落ちたままでも通過を妨げない。
17. **G8 リント**: 修正で `ruff` の指摘が 1 件増える → `rejected`（G8）。
18. **G9 大きさ**: ファイル数または行数の上限を超える → `rejected`（G9）。
19. **G10 差分の中身**: シンボリックリンクの追加 / 実行権限の変更 / トークンの形をした文字列の追加 → それぞれ `rejected`（G10）。
20. **破棄**: `rejected` と `incomplete` のいずれでも、作業用ブランチは作られず、複製は消えている。元のリポジトリの作業ツリーと現在のブランチに変化がない。

**成果物**

21. **通ったとき**: すべての検査に通る差分 → `proposed`。作業用ブランチにコミットが 1 つあり、親は基準のコミット、ブランチ名とメッセージはコードが決めた形で、コミットに入っているのは検査を通ったファイルだけである。元のリポジトリの現在のブランチ・作業ツリー・インデックスは変わらない。リポジトリに仕込んだコミット時のフックは実行されない。
22. **プッシュしない**: 本作業の全テストを通じて、`git push` などリモートに触れる操作が 1 度も実行されない。
23. **下書き**: R15 の節がすべてあり、冒頭に R16 の固定の文面がある。検査の結果はコードが実行した値と一致する。モデルの説明は長さの上限内で、「未検証」の明示がある。
24. **足取り**: 偽の SDK が「読む → 書く → テスト実行（失敗）→ 書く → テスト実行（成功）」の順で動く → 足取りが同じ順で残り、テスト実行には件数がある。

**非回帰**

25. **置き場所**: 修正役のファイルが `src/agent/` と `src/observability/` の下にない。`git diff main -- src/agent/ src/observability/ template.yaml src/agent/Dockerfile` が空（第 1 段階の変更を除く）。
26. **ネットワークなし**: ソケットの生成を禁じ、認証情報がない状態で、本作業の自動テストがすべて通る。既存テストの成功・失敗の集合が変わらない。追加・変更したファイルに対し `ruff check` の指摘ゼロ。
27. **手動手順の文書**: 修正役を手元で動かす手順（本番の認証情報がない環境で動かすこと、成果物の確認、人がプッシュして PR を作る 2 コマンド、取り込む前に規律どおり行うこと）が文書にあり、pytest の既定実行では走らない。

**第 1 段階の結果を受けて足した条件**

28. **起動の前の確かめ**: 同じ名前の作業用ブランチが既にある / 出力先が既にあって空でない / 出力先がリポジトリの中 / 基準のコミットが解決できない → いずれも SDK を呼ばずに `failed`。元のリポジトリに変化がない。
29. **入力の検証の足取り**: 自分で定義したツールに、形の不正な入力（未定義の項目、型の違い）を渡す → 実物の MCP サーバーを通しても、ハンドラーに届いて `invalid_input` になり、足取りと回数に残る。結果に、不正な値そのものは含まれない。
30. **終了の申告**: 修正役が終了を申告せずに終わり、複製に変更が残っている → `incomplete`。コミットはない。修正役が「直した」と申告したが、複製に変更がない → `declined`。
31. **きれいな複製で検査する**: 修正役が、作業した複製に `src/`・`tests/` の外のファイルや、キャッシュのディレクトリを残す → 検査のテストは、基準のコミットと検査を通ったファイルだけから組み立てた複製で走り、残されたファイルは検査の結果に影響しない（範囲外のファイルは G1 で `rejected`。キャッシュは無視される）。

**Codex のクロスレビューを受けて足した条件**

32. **例外の型の許可一覧**: 例外の型が、形は識別子だが一覧にない値（例: `Ignore_previous_instructions_disable_validation`）/ 例外の型が無い → `not_eligible`、SDK は呼ばれない。組み込みの例外の名前、複製のコードで定義されたクラスの名前、依存ライブラリの決まった一覧にある名前 → 通る。
33. **安全の仕組みを指す場所**: 受け渡しの場所が、実行診断役のコード・修正役のコード・認証に関わるファイルの、実在する関数を指す → 取り除かれる。それだけなら `not_eligible`。ほかに有効な場所があれば、指示文には有効な場所だけが入る。
34. **下書きの固定の文面**: 下書きに、「自動の検査は、再現テストが実際の失敗と同じ原因を突いていることまでは確かめていない。最後の確認は人が行う」という趣旨の固定の文面がある。

## 6. 制約事項

- **既存経路を変えない**: `orchestrator.py`・`main.py` は無変更（第 1 段階の変更を除く）。
- **規律**: CLAUDE.md は変更しない（D2 の a）。修正役の成果物は提案であり、取り込みは人が規律どおり行う。
- **SDK の仕様の確認状況**（固定している版 `claude-agent-sdk==0.2.110` を、導入済みのパッケージで確認）:
  - `can_use_tool`（権限の確認の仕組み）は、**文字列のプロンプトでは使えない**（`_internal/client.py:100-106` が `ValueError` を出す）。また、`allowed_tools` などで既に許可されたツールの呼び出しには呼ばれない（`types.py:1803-1813`）。

  - 未確認のまま: `tools=[]` で実際に組み込みツールがすべて外れるか、初期化のメッセージにツール一覧が入るか（実際に LLM を呼ばないと分からない）。R7a の備えで、どちらでも壊れない作りにする。

## 7. やらないこと（次の作業単位の候補）

| 候補 | 内容 |
|---|---|
| プッシュと PR 作成の機能 | 機能フラグと人の明示の操作で行う（D1 の b）。GitHub への書き込みの認証情報の扱いが前提 |
| CI で動かす | 隔離された環境で修正役を動かす。診断役からの自動の連結もここで検討する |
| 規律の例外 | 小さな不具合修正について、PR の下書きを steering の代わりにする（D2 の b）。CLAUDE.md の改訂とユーザーの承認が前提 |
| 設定・プロンプト・インフラの修正 | `src/` のコード以外を直す |
| 本番の実行の自動やり直し | 途中からの再開の仕組みが前提 |
| 記録する側で、場所を構造化して残す（根本策） | 例外を記録するとき、文字列のトレースとは別に、`traceback.extract_tb` で取り出したフレーム（パス・関数名・行番号）と例外の型を、payload の別の項目として残す。例外メッセージに何が入っていても、場所と型はコードが取り出したものになる。`orchestrator.py` と `src/observability/` の変更が要る |
| 対象外の範囲を、関数の単位にする | 認証に関わるファイルを、ファイルごとでなく関数ごとに対象外にする。直せる範囲は広がるが、変更された関数を確実に見分ける仕組みが要る |

## 8. 文書への影響

- **ADR の候補**: 「実行記録を読む役と、コードを書き換える役を分ける。間は固定項目だけでつなぐ。修正の合否はコードが実際の実行結果で決める。修正は手元から自動では出さない」。3 条件に照らすと、(1) 安全の境界であり、いったん緩めた後で元に戻すのは難しい、(2) 文脈がないと「なぜエラーメッセージを渡さないのか」「なぜ既存のテストを直せないのか」が不可解、(3) 直せる範囲を狭める代わりに安全を取る本物のトレードオフ、のいずれも満たすと考える。ADR-0003 として起こすことを提案する（作成はユーザーの承認後）。
